# 意訳作業の引き継ぎ：次のエージェントへ

このリポジトリでは、公式Handbookの原文を固定し、全節の情報を保って読みやすい日本語へ意訳します。**章番号だけで対象を決めず、章名・上流パス・保存済み原文・ユーザーの指定を照合してから着手してください。** 以下は2026-11-04までの作業方法と、継続時に必要な注意点です。

## 最初に読むもの

- [README](../README.md)：目的と進捗。ログは過去の時点の記録なので、現在のファイル・PR状態と照合します。
- [SOURCE](../SOURCE.md)：原文の出典、取得時点、不明な来歴。
- [目次](../handbook/TOC.md)：対応ファイルと状態。既存IDと公式章番号が一致しない箇所があります。
- 対象範囲のマニフェストと検証記録。第26〜27章なら [JSON](translation-ch26-ch27.json) と [記録](translation-ch26-ch27.md)。
- [用語集](../handbook/ja/glossary.md)、近い分野の既存訳、[LICENSE](../LICENSE)。

作業ツリーの変更、現在のブランチ、PRのheadとbase、レビュー・承認状況も調べます。他の作業の変更を取り込んだり消したりせず、新しい作業は通常、最新mainを基点とする専用ブランチにします。同じPRへの追加依頼なら、そのPRのブランチで続けます。

## 章番号の対応を先に確定する

上流でネットワーク章が独立したため、既存目次・ファイル名と公式番号が混在しています。現在の対応例です。

| 内容 | 既存TOCのID | 固定上流の公式章番号 | 訳文 |
|---|---:|---:|---|
| Desktop Applications | 07 | 08 | `handbook/ja/07-desktop.md` |
| Booting Process | 14 | 15 | `handbook/ja/14-boot.md` |
| ZFS | 22 | 23 | `handbook/ja/23-zfs.md` |
| Other File Systems | 23 | 24 | `handbook/ja/24-filesystems.md` |
| Localization | 25 | 26 | `handbook/ja/26-l10n.md` |
| Updating and Upgrading | 26 | 27 | `handbook/ja/27-cutting-edge.md` |

公式Chapter 23をVirtualizationと取り違えるなど、旧目次の番号だけで範囲を選ばないでください。ユーザーが章名を指定した場合は、その内容を優先します。新しい上流のfront matterにあるtitleと章見出しも確認し、マニフェストへ `id`、`upstream_chapter_number`、必要なら `legacy_toc_id` を記録します。既存章の一括改番は、別途依頼がある場合の作業です。

## 原文を固定して出典を残す

1. 上流 `freebsd/freebsd-doc` の対象コミットと、`documentation/content/en/books/handbook/<slug>/_index.adoc` を確定します。複数章は、特別な理由がなければ同じコミットを使います。
2. 原文を改変せず `handbook/en/<対象範囲>/` に保存し、SHA-256を計算します。マニフェストに上流リポジトリ、コミット、取得日、原文・訳文のパス、ハッシュ、状態を記録します。
3. 原文にリリース属性があれば、同じコミットの `shared/releases.adoc` など必要な定義も固定します。本文では解決した値とその時点を説明し、コマンド中に残す属性は置換方法を説明します。pkg設定の `${ABI}` など、実行環境が扱う変数は文書属性と区別します。
4. 画像は原文と同じコミットの `documentation/static/images/books/handbook/<slug>/` を参照し、パスの存在と並び順を確認します。浮動するmainの画像URLと混ぜません。
5. 原文更新時は差分を読み、訳文を再照合してからハッシュ・進捗を更新します。検査を通すためだけにハッシュを書き換えません。

第1〜14・23〜24・26〜27章は `a39743a3b0535f4498735119317889ea2bdfeb28` に固定しました。これは将来の作業でも常に最新という意味ではありません。次の作業で使う基点を調べ、以前の固定版との関係を記録してください。

第16章は例外で、元の上流コミットと取得日時が不明です。[jails-source.json](jails-source.json)にあるリポジトリ内の基点や原文追加日から、上流の来歴を推定しないでください。

## 意訳の方針

- 英文の語順より、操作・目的・条件が自然につながる日本語を優先します。段落を整理しても、節、選択肢、前提、例外、警告、表の情報を落としません。
- コマンド、設定、出力例は原文を保持します。変更する必要がある誤記は、元の例と修正・注意を訳注で区別します。コード例を黙って「最新化」しません。
- シェルの `#`・`%` はプロンプトであると必要に応じて説明します。掲載コマンドを翻訳作業中に実行しません。とくにdd、newfs、rm、プール破棄、OS更新、再起動などは文書中の例です。
- 過去のリリース番号、旧パッケージ名、syscons、古い文字コード、実験的なpkgbaseなどは、固定原文の時点と適用条件を示します。古い例を現在の推奨手順として断言しません。
- 訳者の補足は「訳注」などで原文と区別します。技術的な食い違いを補う場合は、FreeBSDの該当版のマニュアルやOpenZFSの公式文書など一次資料を確認し、リンクと確認範囲を残します。
- 一次資料を確認していない推測を、原文の訂正として書きません。情報が足りなければ、不明な範囲を示して追加確認します。
- UI項目名、プロパティ名、デバイス名、Portのoriginは対応を追えるよう保持します。デバイス名・利用者名などの置換条件も説明します。
- 用語は既存訳・用語集へ合わせます。意味を省いた機械的な要約や、原文コードだけを置いた節で「意訳済み」にしません。

## Markdownへ変換するときの注意

原文の見出しの階層と順序を維持します。明示IDは `<a id="...得られたID..."></a>` の形で残します。アンカーのない見出しは、共通検査器が期待する `chapter-NN-heading-XX` 形式を使います。XXは章全体での見出しの1始まりの順番です。実際のIDは `scripts/check_handbook_translations.py` の `source_sections` と照合してください。

本文・表セルに埋め込まれたIDも対象です。用語のアンカーは、用語集の先頭へ全部集めず、各説明へ置きます。画像・表のIDも対応する位置へ置きます。長い用語表を説明の並びへ展開するなどの変更は、全項目の保持とリンク先の位置を手動確認し、変更した構造を検証記録へ書きます。

コードフェンスを閉じ、AsciiDocの `crossref:`、`man:...[]`、`package:...[]`、属性、未置換の作業記号を本文に残しません。原文の節末が空でも、節の目的が分かる日本語を添えます。章内リンクは明示ID、翻訳済みの章間リンクは実在する訳文・IDを使い、未翻訳章は公式文書の適切なページへリンクします。

AsciiDocのコード区切りは四つ以上のドットやハイフンが使われます。コード内の見出し風の行、注釈、追加アンカーもあるので、単純な文字列置換だけでは変換できません。注釈 `<.>` を除いた最終行が空になる場合もあります。PR #7では、このケースで共通検査器の期待値を末尾正規化する修正を行いました。実コードの差を見逃すような正規化は加えないでください。

## 実際の作業順序

1. 対象と原文を固定し、全見出し・アンカー・コード・画像・表と、警告や版条件を洗い出します。
2. 原文を節単位で読み、意訳します。長い章は分割して進め、どこまで終えたかを記録します。既存ドラフトも実際に読み、訳抜け・途中切れを照合します。
3. 原文と訳文を並べて自己校正します。否定、数値・単位、権限、実行順序、削除範囲、バージョン条件、全表の行、注釈の説明も確認します。
4. 範囲用のマニフェスト・検査用エントリーポイント・CIを用意します。既存範囲のID一覧を流用したままにせず、新しい対象IDへ合わせます。
5. 機械検査とMarkdown解析、画像・リンクの確認を行います。不備が出たら、まず原文・訳文・検査器のどこが原因かを調べます。検査器を修正した場合は、検出すべき不備の負例と影響する既存範囲を再確認します。
6. 全節の自己校正が済んでから `translated` にします。途中は `pending` とし、通常検査の成功を全章完成と扱いません。
7. README・SOURCE・TOC・マニフェスト・検証記録を更新し、PRを作成・更新します。CIの結果は提出するheadで確認し、承認を依頼します。

## 検証の入口と限界

リポジトリのルートで実行します。Python 3を使用し、これらのスクリプト自体に追加Pythonパッケージは不要です。

```shell
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check_handbook_translations.py --require-complete
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check_jails_translation.py
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check_ch23_ch24_translations.py --require-complete
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check_ch19_ch20_translations.py --require-complete
PYTHONDONTWRITEBYTECODE=1 python3 scripts/check_ch26_ch27_translations.py --require-complete
git diff --check
```

変更範囲に合う検査を実行します。共通検査器を変えた場合は利用している範囲へ広げます。`--require-complete` は未完了状態を失敗にする指定です。第16章の検査器にはこのオプションを付けません。

| 確認項目 | 証拠と注意点 |
|---|---|
| 原文の同一性 | 保存ファイルとマニフェストのSHA-256。ハッシュ一致は原文の技術的正確さを保証しません。 |
| 節・コード・画像 | 共通verifyで順序、階層、ID、コード内容、固定コミットの画像参照などを確認。原文の全構文に対応する汎用AsciiDocパーサではありません。 |
| リンク | 範囲用検査で章内ID・相対ファイルを確認。第23〜24・26〜27章用は章間の明示フラグメントも確認します。第1〜14章用の章間フラグメントは別途確認が必要です。外部URLの現在の応答はこれらの検査では確認しません。 |
| 表・レンダリング | PandocのGFM解析と原文との手動照合。表・行の欠落や自然な表示は、上の構造検査だけでは保証されません。必要に応じてレンダリングも確認します。 |
| 訳文の意味 | 原文との手動照合。日本語が存在するという機械判定だけでは不十分です。 |
| マニフェストのcounts | 実ファイルの数値と別途照合。記載しただけで検査器が全項目を保証するわけではありません。 |
| 実機・専門校閲 | 実施した対象・環境・結果を別に記録。未実施ならそのまま明記します。 |

Pandocを用意した環境では、次のようにGFMとして解析できます。`chapter.md` は確認対象の訳文パスへ置き換えます。

```shell
pandoc --from=gfm --to=json chapter.md > /tmp/chapter-ast.json
```

ASTのHeader・CodeBlock・Tableや、画像参照の件数を実ファイル・マニフェストと比較します。解析成功だけでレイアウトや内容の正確さを判断しません。画像は上流の固定コミットのツリー内にも存在するか確認します。

## 一時ファイルに依存しない引き継ぎ

これまでの作業では、節単位の草稿JSON、コード・画像を埋め込む補助スクリプト、Pandoc集計や負例検査のスクリプトを作業環境の `/tmp` に置きました。**これらはリポジトリに同梱されず、次の環境に残る保証もありません。** 完成したMarkdown、固定原文、マニフェスト、コミット済み検査器、検証記録を引き継ぎ元にしてください。

節へのコード再配置を自動化する場合も、順序と内容を照合し、出力を通読します。中断する場合は、完了した節と残る節、未確認事項をリポジトリ内の作業記録とコミットへ残し、一時草稿だけを成果としません。認証情報や作業環境固有の秘密は記録・コミットしません。

## PRと承認

PRには対象章名、公式番号との対応、固定原文、変更点、実行した検査と限界を記載します。まだ途中ならDraftとし、完了後にレビュー可能へ変えます。CIが緑でも、手動照合が未完了なら完成扱いにしません。

**この作業の承認手順は、具体的なPRを示してユーザーに承認を求め、確認できた後にマージする流れです。** 以前のPRへの承認を、新しいPRへ自動的に適用しません。コメントの追記・修正依頼も、単独ではマージ承認ではありません。ユーザーはこれまでリベースマージを選んでいますが、実行時には対象PRと承認内容を確認してください。

マージ時は、承認されたhead、最新のチェック結果、競合の有無を確認し、可能なら期待するhead SHAを指定します。マージ後はGitHubのmerged状態を確認して報告します。ユーザーの修正依頼が来たら同じPRへ反映し、変更した範囲の検証結果を更新します。
