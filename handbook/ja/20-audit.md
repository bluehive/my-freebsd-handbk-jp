# 第20章 セキュリティイベント監査（Security Event Auditing）

本章では、FreeBSDのセキュリティイベント監査（audit）の導入と設定、監査ポリシーの考え方、監査記録（トレイル）の見方を説明します。例の設定は仕組みを理解するための出発点で、運用する環境の要件に合わせて調整してください。

<a id="audit-synopsis"></a>
## 概要

FreeBSDには、セキュリティイベント監査の機能が含まれています。イベント監査は、ログイン、設定変更、ファイルやネットワークへのアクセスなど、セキュリティに関わるさまざまなシステムイベントを、信頼性の高い形で、細かく、設定に従って記録します。この記録は、稼働中のシステムの監視、侵入の検知、事後の分析にとって非常に貴重な情報になります。FreeBSDは、Sunが公開したBasic Security Module（BSM）のアプリケーションプログラミングインターフェイス（API）とファイル形式を実装しており、SolarisやMac OS Xの監査の実装と相互運用できます。

本章では、イベント監査の導入と設定を中心に説明します。監査ポリシーを説明し、監査設定の例も示します。

本章で学ぶ内容は次のとおりです。

* イベント監査とは何か、どのように働くか
* FreeBSDで、利用者とプロセスを対象にイベント監査を設定する方法
* 監査記録の削減・閲覧ツールを使って、監査証跡（audit trail）を確認する方法

本章を読む前に、次の知識が必要です。

* UNIXとFreeBSDの基本を理解していること（[FreeBSDの基本](03-basics.md#basics)）
* カーネルの設定とコンパイルの基本に慣れていること（[FreeBSDカーネルの設定](09-kernelconfig.md#kernelconfig)）
* セキュリティと、それがFreeBSDにどう関わるかをある程度知っていること（[セキュリティ](https://docs.freebsd.org/en/books/handbook/security/#security)）

> **警告**: 監査機能には、既知の制限があります。セキュリティに関わるすべてのシステムイベントを監査できるわけではありません。また、Xorgベースのディスプレイマネージャーやサードパーティ製のデーモンなど、一部のログイン機構は、利用者のログインセッションに対して監査を正しく設定しません。
>
> セキュリティイベント監査の機能は、システムの活動をきわめて詳細に記録できます。忙しいシステムで詳細度を高く設定すると、トレイルファイルのデータが非常に大きくなり、設定によっては1週間でギガバイト単位に達することもあります。管理者は、大量の監査を行う設定に必要なディスク容量を考慮しなければなりません。たとえば、`/var/audit` 専用のファイルシステムを用意しておくと、監査用のファイルシステムが満杯になっても、ほかのファイルシステムに影響しません。

<a id="audit-inline-glossary"></a>
## 主要な用語

セキュリティイベント監査に関連する用語は、次のとおりです。

* *event*（イベント）: 監査サブシステムで記録できるイベントを、監査可能なイベントといいます。セキュリティに関わるイベントの例には、ファイルの作成、ネットワーク接続の確立、利用者のログインなどがあります。イベントには、認証された利用者に結び付けられる「帰属可能（attributable）」なものと、そうでない「帰属不能（non-attributable）」なものがあります。帰属不能なイベントの例は、パスワードの誤入力など、ログイン処理で認証が済む前に起こるイベントです。
* *class*（クラス）: 選択式で使う、関連するイベントをまとめて名前を付けた集合です。よく使われるイベントクラスには、「ファイル作成」（fc）、「実行」（ex）、「ログイン・ログアウト」（lo）などがあります。
* *record*（記録）: セキュリティイベントを記述した監査ログの項目です。記録には、記録イベントの種類、操作を行った主体（利用者）の情報、日付と時刻、対象や引数の情報、成功か失敗かの状態が含まれます。
* *trail*（トレイル）: セキュリティイベントを記述した一連の監査記録からなるログファイルです。トレイルは、イベントが完了した時刻におおむね沿った順序で並びます。監査トレイルに記録をコミットできるのは、認可されたプロセスだけです。
* *selection expression*（選択式）: イベントに一致させるための、接頭辞と監査イベントクラス名のリストを含む文字列です。
* *preselection*（事前選択）: 管理者が関心を持つイベントを、システムが識別する処理です。事前選択の設定では、一連の選択式を使って、どの利用者についてどのクラスのイベントを監査するかを指定するほか、認証済みのプロセスと未認証のプロセスの両方に適用される全体設定も指定します。
* *reduction*（削減）: 既存の監査トレイルから、保存・印刷・分析のために記録を選び出す処理です。同じく、不要な監査記録をトレイルから取り除く処理も指します。削減を使うと、管理者は監査データの保存ポリシーを実現できます。たとえば、詳細な監査トレイルは1か月間だけ保存し、それ以降はトレイルを削減して、保管用にログイン情報だけを残すといった運用ができます。

<a id="audit-config"></a>
## 監査の設定

イベント監査のユーザー空間側のサポートは、FreeBSDの基本システムの一部としてインストールされます。カーネル側のサポートは、既定で `GENERIC` カーネルに含まれています。`auditd(8)` は、`/etc/rc.conf` に次の行を追加すると有効になります。

```
auditd_enable="YES"
```

そのあと、監査デーモンを起動します。

```shell
# service auditd start
```

独自のカーネルをコンパイルする場合は、カスタムカーネルの設定ファイルに次の行を含める必要があります。

```
options	AUDIT
```

<a id="chapter-20-heading-05"></a>
### イベント選択式

選択式は、監査設定のさまざまな場所で、どのイベントを監査するかを決めるために使います。式には、一致させるイベントクラスのリストを書きます。選択式は左から右へ評価され、2つの式は、一方をもう一方の後ろに連結することで結合されます。

[既定の監査イベントクラス](#event-selection)の表に、既定の監査イベントクラスをまとめます。

<a id="event-selection"></a>
**既定の監査イベントクラス**

| クラス名 | 説明 | 動作 |
|---|---|---|
| `all` | all（すべて） | すべてのイベントクラスに一致します。 |
| `aa` | authentication and authorization（認証と認可） | |
| `ad` | administrative（管理） | システム全体に対して行われる管理上の操作。 |
| `ap` | application（アプリケーション） | アプリケーションが定義した操作。 |
| `cl` | file close（ファイルのクローズ） | `close` システムコールの呼び出しを監査します。 |
| `ex` | exec（実行） | プログラムの実行を監査します。コマンドライン引数と環境変数の監査は、`audit_control(5)` の `policy` 設定にある `argv` と `envv` のパラメーターで制御します。 |
| `fa` | file attribute access（ファイル属性へのアクセス） | `stat(1)` や `pathconf(2)` など、客体の属性へのアクセスを監査します。 |
| `fc` | file create（ファイルの作成） | 結果としてファイルが作成されるイベントを監査します。 |
| `fd` | file delete（ファイルの削除） | ファイルの削除が行われるイベントを監査します。 |
| `fm` | file attribute modify（ファイル属性の変更） | `chown(8)`、`chflags(1)`、`flock(2)` など、ファイル属性の変更が行われるイベントを監査します。 |
| `fr` | file read（ファイルの読み取り） | データが読み取られる、またはファイルが読み取り用に開かれるイベントを監査します。 |
| `fw` | file write（ファイルの書き込み） | データが書き込まれる、またはファイルが書き込み・変更されるイベントを監査します。 |
| `io` | ioctl | `ioctl` システムコールの使用を監査します。 |
| `ip` | ipc | POSIXパイプやSystem V IPC操作を含む、さまざまな形のプロセス間通信（IPC）を監査します。 |
| `lo` | login_logout | `login(1)` と `logout(1)` のイベントを監査します。 |
| `na` | non attributable（帰属不能） | 帰属不能なイベントを監査します。 |
| `no` | invalid class（無効なクラス） | どの監査イベントにも一致しません。 |
| `nt` | network（ネットワーク） | `connect(2)` や `accept(2)` など、ネットワーク操作に関するイベントを監査します。 |
| `ot` | other（その他） | そのほかのさまざまなイベントを監査します。 |
| `pc` | process（プロセス） | `exec(3)` や `exit(3)` など、プロセスの操作を監査します。 |

これらの監査イベントクラスは、設定ファイル `audit_class` と `audit_event` を変更することでカスタマイズできます。

各監査イベントクラスには、成功した操作と失敗した操作のどちらに一致させるか、またそのクラスと種類の一致を追加するのか除外するのかを示す接頭辞を組み合わせられます。[監査イベントクラスの接頭辞](#event-prefixes)の表に、使える接頭辞をまとめます。

<a id="event-prefixes"></a>
**監査イベントクラスの接頭辞**

| 接頭辞 | 動作 |
|---|---|
| `+` | このクラスのうち、成功したイベントを監査します。 |
| `-` | このクラスのうち、失敗したイベントを監査します。 |
| `^` | このクラスについて、成功したイベントも失敗したイベントも監査しません。 |
| `^+` | このクラスのうち、成功したイベントを監査しません。 |
| `^-` | このクラスのうち、失敗したイベントを監査しません。 |

接頭辞がない場合は、そのイベントの成功した場合と失敗した場合の両方が監査されます。

次の選択式の例は、ログイン・ログアウトのイベントは成功も失敗も、実行イベントは成功したものだけを選択します。

```
lo,+ex
```

<a id="chapter-20-heading-06"></a>
### 設定ファイル

セキュリティイベント監査の設定ファイルは、次のとおり `/etc/security` にあります。

* `audit_class`: 監査クラスの定義を含みます。
* `audit_control`: 既定の監査クラス、監査ログのボリュームに残しておく最小のディスク容量、監査トレイルの最大サイズなど、監査サブシステムの各種の動作を制御します。
* `audit_event`: システムの監査イベントの名前と説明、および各イベントがどのクラスに属するかの一覧を含みます。
* `audit_user`: ログイン時に全体の既定値と組み合わせて使う、利用者ごとの監査要件を定めます。
* `audit_warn`: 監査記録の空き容量が少なくなったときや、監査トレイルファイルがローテーションされたときなど、例外的な状況で、`auditd(8)` が警告メッセージを生成するために使う、カスタマイズ可能なシェルスクリプトです。

> **警告**: 監査の設定ファイルは、慎重に編集・管理してください。設定を誤ると、イベントが正しく記録されなくなるおそれがあります。

ほとんどの場合、管理者が変更する必要があるのは、`audit_control` と `audit_user` だけです。前者はシステム全体の監査の特性とポリシーを制御し、後者は利用者ごとの監査を細かく調整するために使えます。

<a id="audit-auditcontrol"></a>
#### `audit_control` ファイル

監査サブシステムの既定値の多くは、`audit_control` で指定します。

```
dir:/var/audit
dist:off
flags:lo,aa
minfree:5
naflags:lo,aa
policy:cnt,argv
filesz:2M
expire-after:10M
```

`dir` エントリは、監査ログを保存する1つ以上のディレクトリを設定します。`dir` エントリが複数ある場合は、順に、いっぱいになるたびに次のディレクトリが使われます。監査ログは専用のファイルシステムに保存するよう設定するのが一般的です。そうしておけば、ファイルシステムがいっぱいになったときに、監査サブシステムとほかのサブシステムが互いに干渉するのを防げます。

`dist` フィールドを `on` または `yes` に設定すると、すべてのトレイルファイルへのハードリンクが `/var/audit/dist` に作成されます。

`flags` フィールドは、帰属可能なイベントに対する、システム全体の既定の事前選択マスクを設定します。上の例では、すべての利用者について、ログイン・ログアウトに加えて、認証と認可のイベントが、成功も失敗も監査されます。

`minfree` エントリは、監査トレイルを保存するファイルシステムに残しておく空き容量の最小の割合を定めます。

`naflags` エントリは、ログイン・ログアウトの処理や認証・認可など、帰属しないイベントについて監査する監査クラスを指定します。

`policy` エントリは、監査の動作のさまざまな面を制御するポリシーフラグを、カンマ区切りで指定します。`cnt` は、監査に失敗してもシステムの動作を継続することを示します（このフラグを使うことを強く勧めます）。もう一つのフラグ `argv` は、コマンド実行の一部として、`execve(2)` システムコールに渡されたコマンドライン引数を監査します。

`filesz` エントリは、監査トレイルが自動的に終了されてローテーションされるまでの最大サイズを指定します。値を `0` にすると、ログの自動ローテーションが無効になります。指定したファイルサイズが最小値の512kを下回る場合、その指定は無視され、ログメッセージが生成されます。

`expire-after` フィールドは、監査ログファイルがいつ期限切れになって削除されるかを指定します。

> **訳注**: 上の例の `10M` のように、`expire-after` には、最後の書き込みからの経過時間だけでなく、すべてのトレイルファイルの合計サイズ（この例では10MB）や、その両方の組み合わせで期限を指定できます。書式は FreeBSD 15.1の [audit_control(5)](https://man.freebsd.org/cgi/man.cgi?query=audit_control&sektion=5) を確認しました。

<a id="audit-audituser"></a>
#### `audit_user` ファイル

管理者は、`audit_user` で特定の利用者に対する追加の監査要件を指定できます。各行は、2つのフィールドで利用者の監査を設定します。`alwaysaudit` フィールドは、その利用者について常に監査すべきイベントの集合を、`neveraudit` フィールドは、その利用者について決して監査してはならないイベントの集合を指定します。

次のエントリの例は、`root` についてログイン・ログアウトのイベントと成功したコマンド実行を、`www` についてファイルの作成と成功したコマンド実行を監査します。既定の `audit_control` と組み合わせて使う場合、`root` の `lo` エントリは冗長で、`www` についてもログイン・ログアウトのイベントが監査されます。

```
root:lo,+ex:no
www:fc,+ex:no
```

<a id="audit-administration"></a>
## 監査トレイルの扱い

監査トレイルはBSMのバイナリ形式で保存されるため、トレイルを加工したりテキストに変換したりするための組み込みツールがいくつか用意されています。トレイルファイルを単純なテキスト形式に変換するには、`praudit` を使います。分析、保管、印刷のために監査トレイルファイルを絞り込むには、`auditreduce` を使います。このユーティリティは、イベントの種類、イベントクラス、利用者、イベントの日付や時刻、操作対象のファイルパスや客体など、さまざまな選択パラメーターに対応しています。

たとえば、指定した監査ログの内容全体をプレーンテキストでダンプするには、次のようにします。

```shell
# praudit /var/audit/AUDITFILE
```

ここで *AUDITFILE* は、ダンプしたい監査ログです。

監査トレイルは、トークンで構成された一連の監査記録からなり、`praudit` は、それらを1行に1トークンずつ順に出力します。各トークンには `header`（監査記録のヘッダー）や `path`（名前の検索で得たファイルパス）など、特定の種類があります。次は、`execve` イベントの例です。

```
header,133,10,execve(2),0,Mon Sep 25 15:58:03 2006, + 384 msec
exec arg,finger,doug
path,/usr/bin/finger
attribute,555,root,wheel,90,24918,104944
subject,robert,root,wheel,root,wheel,38439,38032,42086,128.232.9.100
return,success,0
trailer,133
```

この監査記録は、`execve` の呼び出しが成功し、コマンド `finger doug` が実行されたことを表しています。`exec arg` トークンには、シェルがカーネルに渡した、処理済みのコマンドラインが入っています。`path` トークンは、カーネルが検索した実行ファイルのパスを保持しています。`attribute` トークンは、そのバイナリを記述し、ファイルモードを含みます。`subject` トークンには、監査ユーザーID、実効ユーザーIDとグループID、実ユーザーIDとグループID、プロセスID、セッションID、ポートID、ログインアドレスが入っています。この例では、監査ユーザーIDと実ユーザーIDが異なっていることに注目してください。利用者 `robert` が、このコマンドを実行する前に `root` アカウントに切り替えたためですが、監査では、最初に認証された利用者の名前が使われています。`return` トークンは実行の成功を示し、`trailer` が記録を締めくくります。

`-x` を付けるとXML出力形式も使えます。

監査ログは非常に大きくなることがあるので、`auditreduce` を使って、記録の一部を選び出せます。次の例は、`AUDITFILE` に保存されている、利用者 `trhodes` が生成したすべての監査記録を選択します。

```shell
# auditreduce -u trhodes /var/audit/AUDITFILE | praudit
```

`audit` グループのメンバーは、`/var/audit` にある監査トレイルを読む権限を持っています。既定ではこのグループは空なので、監査トレイルを読めるのは `root` 利用者だけです。監査の確認権限を委任するには、`audit` グループに利用者を追加します。監査ログの内容を追跡できると、利用者やプロセスの動作に関して非常に多くのことがわかるため、監査の確認権限の委任は慎重に行うことを勧めます。

<a id="chapter-20-heading-10"></a>
### 監査パイプによるリアルタイム監視

監査パイプ（audit pipe）は、アプリケーションが、監査記録のストリームをリアルタイムで取り出せるようにする、クローン型（cloning）の擬似デバイスです。これが主に役立つのは、侵入検知やシステム監視のアプリケーションの作者です。ただし、トレイルファイルの所有者の問題や、ログのローテーションによるイベントストリームの中断に悩まされずに、管理者がリアルタイム監視を行える便利な手段でもあります。監査イベントのリアルタイムのストリームを追跡するには、次のようにします。

```shell
# praudit /dev/auditpipe
```

既定では、監査パイプのデバイスノードにアクセスできるのは `root` 利用者だけです。`audit` グループのメンバーもアクセスできるようにするには、`/etc/devfs.rules` に `devfs` の規則を追加します。

```
add path 'auditpipe*' mode 0440 group audit
```

devfsファイルシステムの設定について詳しくは、`devfs.rules(5)` を参照してください。

> **警告**: 監査イベントのフィードバックの循環は、簡単に作れてしまいます。つまり、監査イベントを見ること自体が、さらに監査イベントを生む状態です。たとえば、ネットワークのI/Oをすべて監査していて、SSHセッションから `praudit` を実行したとします。すると、表示される各イベントがまた別のイベントを生むため、監査イベントが連続して高い頻度で発生します。このため、監査パイプのデバイスに対する `praudit` は、細かいI/O監査を行っていないセッションから実行することを勧めます。

<a id="chapter-20-heading-11"></a>
### 監査トレイルファイルのローテーションと圧縮

監査トレイルはカーネルが書き込み、監査デーモンの `auditd(8)` が管理します。管理者は、`newsyslog.conf(5)` などのツールを使って、監査ログを直接ローテーションしようとしてはいけません。そうではなく、`audit` を使って、監査を停止し、監査システムを再設定し、ログのローテーションを行うべきです。次のコマンドは、監査デーモンに新しい監査ログを作成させ、カーネルに新しいログへ切り替えるよう通知します。古いログは終了処理を受けて名前が変更され、管理者が自由に扱えるようになります。

```shell
# audit -n
```

`auditd(8)` が実行されていない場合、このコマンドは失敗し、エラーメッセージが出力されます。

次の行を `/etc/crontab` に追加すると、このローテーションを12時間ごとに行うようにできます。

```
0     */12       *       *       *       root    /usr/sbin/audit -n
```

この変更は、`/etc/crontab` を保存すると有効になります。

ファイルサイズに基づく監査トレイルファイルの自動ローテーションも、[`audit_control` ファイル](#audit-auditcontrol)で説明した `audit_control` の `filesz` を使えば可能です。

監査トレイルファイルは非常に大きくなりうるため、監査デーモンがファイルを閉じたあとで、トレイルを圧縮したり、別の方法で保管したりしたくなることがよくあります。`audit_warn` スクリプトを使うと、トレイルがローテーションされるときの正常な終了処理など、監査に関連するさまざまなイベントに対して、カスタマイズした処理を実行できます。たとえば、次の内容を `/etc/security/audit_warn` に追加すると、閉じた監査トレイルを圧縮できます。

```
#
# Compress audit trail files on close.
#
if [ "$1" = closefile ]; then
        gzip -9 $2
fi
```

そのほかの保管作業には、トレイルファイルを中央のサーバーへコピーする、古いトレイルファイルを削除する、不要な記録を取り除くよう監査トレイルを削減する、などがあります。このスクリプトは、監査トレイルファイルが正常に終了処理されたときにだけ実行されます。不適切なシャットダウンのあとに、終了処理されないまま残ったトレイルに対しては実行されません。
