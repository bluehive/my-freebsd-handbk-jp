### シングルユーザーモード

FreeBSD のブートメニューには、"Boot Single User" というラベルの付いたオプションがあります。このオプションを選択すると、システムは「シングルユーザーモード」として知られる特別なモードで起動します。このモードは通常、起動しないシステムの修復や、不明になった `root` パスワードのリセットに使用されます。

シングルユーザーモード中は、ネットワークや他の仮想コンソールは利用できません。ただし、システムへの完全な `root` アクセスが可能であり、デフォルトでは `root` パスワードは必要ありません。これらの理由から、このモードで起動するにはキーボードへの物理的なアクセスが必要です。FreeBSD システムのセキュリティを確保する際には、誰がキーボードに物理的にアクセスできるかを考慮することが重要です。

シングルユーザーモードを制御する設定は、`/etc/ttys` のこのセクションにあります:

```
# name  getty                           type  status  comments
#
# If console is marked "insecure", then init will ask for the root password
# when going to single-user mode.
console none                            unknown  off  secure
```

デフォルトでは、ステータスは `secure` に設定されています。これは、キーボードに物理的にアクセスできる人物が重要ではないか、物理的なセキュリティポリシーによって管理されていることを前提としています。この設定が `insecure` に変更された場合、誰でもキーボードにアクセスできるため、環境自体が安全ではないという前提になります。この行が `insecure` に変更されると、ユーザーがシングルユーザーモードで起動することを選択した場合、FreeBSD は `root` パスワードを要求します。

> **注:** _この設定を `insecure` に変更する際は注意してください!_ `root` パスワードを忘れてしまった場合でも、シングルユーザーモードでの起動は可能ですが、FreeBSD の起動プロセスに詳しくない人にとっては難しいかもしれません。

### コンソールのビデオモードの変更

FreeBSD コンソールのデフォルトのビデオモードは、1024x768、1280x1024、またはグラフィックチップとモニターがサポートする他のサイズに調整できます。別のビデオモードを使用するには、`VESA` モジュールをロードします:

```shell
# kldload vesa
```

ハードウェアがサポートするビデオモードを確認するには、`man vidcontrol(1)` を使用します。サポートされているビデオモードの一覧を取得するには、次のコマンドを実行します:

```shell
# vidcontrol -i mode
```

このコマンドの出力には、ハードウェアがサポートするビデオモードが一覧表示されます。新しいビデオモードを選択するには、`root` ユーザーとして `man vidcontrol(1)` を使用してモードを指定します:

```shell
# vidcontrol MODE_279
```

新しいビデオモードが適切であれば、`/etc/rc.conf` に追加することで、起動時に恒久的に設定できます:

```
allscreens_flags="MODE_279"
```

#### スーパーユーザーアカウント

スーパーユーザーアカウントは、通常 `root` と呼ばれ、特権に制限なくシステムを管理するために使用されます。そのため、電子メールの送受信やシステムの一般的な探索、プログラミングなどの日常的なタスクには使用すべきではありません。

スーパーユーザーは、他のユーザーアカウントとは異なり、制限なく操作できるため、スーパーユーザーアカウントの誤用は重大な災害を引き起こす可能性があります。通常のユーザーアカウントは、誤ってオペレーティングシステムを破壊することはありません。そのため、ユーザーアカウントでログインし、コマンドに特別な特権が必要な場合にのみスーパーユーザーになることをお勧めします。

スーパーユーザーとして実行するコマンドは、常に二重、三重に確認してください。余分なスペースや文字の欠落が、取り返しのつかないデータ損失を意味することがあります。

スーパーユーザー特権を得る方法はいくつかあります。`root` としてログインすることもできますが、これは強く推奨されません。

代わりに、`man su(1)` を使ってスーパーユーザーになります。このコマンドを実行するときに `-` を指定すると、ユーザーは root ユーザーの環境も継承します。このコマンドを実行するユーザーは `wheel` グループに属している必要があります。そうでないとコマンドは失敗します。また、ユーザーは `root` ユーザーアカウントのパスワードを知っている必要があります。

この例では、ユーザーは `make install` を実行するためだけにスーパーユーザーになっています。このステップにはスーパーユーザー特権が必要だからです。コマンドが完了すると、ユーザーは `exit` と入力してスーパーユーザーアカウントを抜け、自分のユーザーアカウントの権限に戻ります。

**スーパーユーザーとしてプログラムをインストールする**

```shell
% configure
% make
% su -
Password:
# make install
# exit
%
```

組み込みの `man su(1)` フレームワークは、単一システムまたはシステム管理者が1人だけの小規模ネットワークでうまく機能します。もう1つの方法は、`security/sudo` パッケージまたはポートをインストールすることです。このソフトウェアはアクティビティログを提供し、管理者がどのユーザーがスーパーユーザーとしてどのコマンドを実行できるかを設定できるようにします。

### アカウントの管理

FreeBSD はユーザーアカウントを管理するためのさまざまなコマンドを提供しています。最も一般的なコマンドは、以下の「ユーザーアカウント管理ユーティリティ」にまとめられています。続いて、その使用例をいくつか示します。詳細と使用例については、各ユーティリティのマニュアルページを参照してください。

#### ユーザーアカウント管理ユーティリティ

| コマンド | 概要 |
|---|---|
| `man adduser(8)` | 新しいユーザーを追加するための推奨コマンドラインアプリケーション。 |
| `man rmuser(8)` | ユーザーを削除するための推奨コマンドラインアプリケーション。 |
| `man chpass(1)` | ユーザーデータベース情報を変更するための柔軟なツール。 |
| `man passwd(1)` | ユーザーパスワードを変更するためのコマンドラインツール。 |
| `man pw(8)` | ユーザーアカウントのあらゆる側面を変更するための強力で柔軟なツール。 |
| `man bsdconfig(8)` | アカウント管理をサポートするシステム設定ユーティリティ。 |

#### ユーザーの追加

新しいユーザーを追加するための推奨プログラムは `man adduser(8)` です。新しいユーザーが追加されると、このプログラムは `/etc/passwd` と `/etc/group` を自動的に更新します。また、新しいユーザーのホームディレクトリを作成し、`/usr/share/skel` からデフォルトの設定ファイルをコピーし、オプションで新しいユーザーにウェルカムメッセージを送信します。このユーティリティはスーパーユーザーとして実行する必要があります。

`man adduser(8)` ユーティリティは対話型で、新しいユーザーアカウントを作成する手順を順に進めます。以下の「FreeBSD でのユーザーの追加」で示されているように、必要な情報を入力するか、Return キーを押して角括弧で示されたデフォルト値を受け入れます。この例では、ユーザーは `wheel` グループに招待されており、`man su(1)` でスーパーユーザーになることができます。終了すると、ユーティリティは別のユーザーを作成するか、終了するかを尋ねます。

**FreeBSD でのユーザーの追加**

```shell
# adduser
```

出力は次のようになります。

```text
Username: jru
Full name: J. Random User
Uid (Leave empty for default):
Login group [jru]:
Login group is jru. Invite jru into other groups? []: wheel
Login class [default]:
Shell (sh csh tcsh zsh nologin) [sh]: zsh
Home directory [/home/jru]:
Home direc
```





% id jru
```

出力は以下のようになります。

```shell
uid=1001(jru) gid=1001(jru) groups=1001(jru), 1100(teamtwo)
```

この例では、`jru` はグループ `jru` と `teamtwo` のメンバーです。

このコマンドと `/etc/group` の形式の詳細については、`man pw(8)` と `man group(5)` を参照してください。

## パーミッション

FreeBSD では、すべてのファイルとディレクトリには関連する一連のパーミッションがあり、これらのパーミッションを表示・変更するためのユーティリティがいくつか用意されています。パーミッションの仕組みを理解することは、ユーザーが必要なファイルにアクセスできる一方、オペレーティングシステムが使用するファイルや他のユーザーが所有するファイルに不適切にアクセスできないようにするために必要です。

この節では、FreeBSD で使われる従来の UNIX(R) パーミッションについて説明します。より細かいファイルシステムアクセス制御については、「Access Control Lists（ACL）」を参照してください。

UNIX(R) では、基本パーミッションは読み取り (read)、書き込み (write)、実行 (execute) の 3 種類のアクセスを使って割り当てられます。これらのアクセス種別は、ファイルの所有者、グループ、およびその他のユーザー（その他全員）に対するファイルアクセスを決めるために使われます。読み取り、書き込み、実行のパーミッションは、それぞれ `r`、`w`、`x` という文字で表すことができます。また、各パーミッションはオンまたはオフ（`0`）のどちらかであるため、2 進数で表すこともできます。数値で表す場合、順序は常に `rwx` として読み取られ、`r` のオン値は `4`、`w` のオン値は `2`、`x` のオン値は `1` です。

表 4.1 に、数値と文字によるパーミッションの可能な組み合わせをまとめます。「ディレクトリリスト」の列を読むとき、`-` はオフに設定されたパーミッションを表します。

**表 4.1 UNIX(R) パーミッション**

| 値 | パーミッション | ディレクトリリスト |
| --- | --- | --- |
| 0 | 読み取りなし、書き込みなし、実行なし | `---` |
| 1 | 読み取りなし、書き込みなし、実行 | `--x` |
| 2 | 読み取りなし、書き込み、実行なし | `-w-` |
| 3 | 読み取りなし、書き込み、実行 | `-wx` |
| 4 | 読み取り、書き込みなし、実行なし | `r--` |
| 5 | 読み取り、書き込みなし、実行 | `r-x` |
| 6 | 読み取り、書き込み、実行なし | `rw-` |
| 7 | 読み取り、書き込み、実行 | `rwx` |

`man ls(1)` に `-l` 引数を指定すると、所有者、グループ、およびその他のユーザーに対するファイルのパーミッションに関する情報の列を含む長いディレクトリリストを表示できます。例えば、任意のディレクトリで `ls -l` を実行すると、次のように表示されます。

```shell
% ls -l
```

出力は次のようになります。

```text
total 530
-rw-r--r--  1 root  wheel     512 Sep  5 12:31 myfile
-rw-r--r--  1 root  wheel     512 Sep  5 12:31 otherfile
-rw-r--r--  1 root  wheel    7680 Sep  5 12:31 email.txt
```

`myfile` の行に注目すると、最初の（左端の）文字は、このファイルが通常のファイル、ディレクトリ、特殊キャラクタデバイス、ソケット、またはその他の特別な擬似ファイルデバイスのいずれであるかを示します。この例では、`-` は通常のファイルを示します。次の 3 文字（この例では `rw-`）は、ファイルの所有者に対するパーミッションです。その次の 3 文字（`r--`）は、ファイルが属するグループに対するパーミッションです。最後の 3 文字（`r--`）は、その他の全ユーザーに対するパーミッションです。ダッシュは、そのパーミッションがオフであることを意味します。この例では、所有者はファイルを読み書きでき、グループはファイルを読み取ることができ、その他の全ユーザーはファイルを読み取りのみできるようにパーミッションが設定されています。上記の表によると、このファイルのパーミッションは `644` となり、各数字がファイルのパーミッションの 3 つの部分を表します。

システムはデバイス上のパーミッションをどのように制御しているのでしょうか。FreeBSD はほとんどのハードウェアデバイスを、プログラムが開いてデータを読み書きできるファイルとして扱います。これらの特別なデバイスファイルは `/dev/` に保存されます。

ディレクトリもファイルとして扱われます。ディレクトリには読み取り、書き込み、実行のパーミッションがあります。ディレクトリの実行ビットは、ファイルのそれとは少し意味が異なります。ディレクトリに実行パーミッションが設定されている場合、`man cd(1)` を使ってそのディレクトリに移動できることを意味します。また、そのディレクトリ内のファイルに、ファイル自体のパーミッションに従ってアクセスできることも意味します。

ディレクトリの一覧を表示するには、ディレクトリに読み取りパーミッションが設定されている必要があります。名前がわかっているファイルを削除するには、そのファイルが含まれるディレクトリに書き込み _および_ 実行パーミッションが必要です。

これ以外にもパーミッションビットはありますが、これは主に setuid バイナリやスティッキーディレクトリといった特別な状況で使われます。ファイルパーミッションとその設定方法の詳細については、`man chmod(1)` を参照してください。

### シンボリックパーミッション

シンボリックパーミッションは、8 進数の値の代わりに文字を使ってファイルやディレクトリにパーミッションを割り当てます。シンボリックパーミッションは、(who) (action) (permissions) という構文を使います。ここで、以下の値が利用可能です。

| 種別 | 文字 | 意味 |
|------|------|------|
| (who) | u | ユーザー |
| (who) | g | グループ所有者 |
| (who) | o | その他 |
| (who) | a | すべて（"world"） |
| (action) | + | 権限の追加 |
| (action) | - | 権限の削除 |
| (action) | = | 権限の明示的な設定 |
| (permissions) | r | 読み取り |
| (permissions) | w | 書き込み |
| (permissions) | x | 実行 |
| (permissions) | t | スティッキービット |
| (permissions) | s | UID または GID の設定 |

これらの値は `man chmod(1)` で使用されますが、数字ではなく文字を使用します。
たとえば、次のコマンドは、`_FILE_` に関連するグループのメンバーと、その他のすべてのユーザーによる `_FILE_` へのアクセスを拒否します。

```shell
% chmod go= FILE
```

ファイルに対して複数の変更を行わなければならない場合は、カンマ区切りのリストを指定できます。
たとえば、次のコマンドは `_FILE_` からグループと「その他のユーザー」の書き込み権限を削除し、全員に実行権限を追加します。

```shell
% chmod go-w,a+x FILE
```

### FreeBSD ファイルフラグ

ファイル権限に加えて、FreeBSD は「ファイルフラグ」の使用をサポートしています。
これらのフラグは、ファイル（ディレクトリではありません）に対するセキュリティと制御の追加レベルを提供します。
ファイルフラグを使うと、`root` でもファイルの削除や変更ができないようにできます。

ファイルフラグは `man chflags(1)` を使って変更します。
たとえば、ファイル `file1` にシステムの削除不可フラグを有効にするには、次のコマンドを実行します。

```shell
# chflags sunlink file1
```

システムの削除不可フラグを無効にするには、`sunlink` の前に "no" を付けます。

```shell
# chflags nosunlink file1
```

ファイルのフラグを表示するには、`man ls(1)` で `-lo` を使用します。

```shell
# ls -lo file1
```

```text
-rw-r--r--  1 trhodes  trhodes  sunlnk 0 Mar  1 05:54 file1
```

いくつかのファイルフラグは `root` ユーザーだけが追加または削除できます。
それ以外の場合、ファイル所有者がファイルフラグを設定できます。
詳細については `man chflags(1)` と `man chflags(2)` を参照してください。

### setuid、setgid、および sticky 権限

これまでに説明した権限のほかに、すべての管理者が知っておくべき特別な設定が 3 つあります。
それらは `setuid`、`setgid`、`sticky` の各権限です。

これらの設定は、通常のユーザーには通常許可されていない機能を提供するため、一部の UNIX(R) 操作にとって重要です。
これらを理解するには、実ユーザー ID と実効ユーザー ID の違いを理解しておく必要があります。

実ユーザー ID は、プロセスを所有または起動する UID です。
実効 UID は、プロセスが実際に実行されるユーザー ID です。
例として、ユーザーがパスワードを変更するとき、`man passwd(1)` は実ユーザー ID で実行されます。
しかし、パスワードデータベースを更新するため、このコマンドは `root` ユーザーの実効 ID として実行されます。
これにより、ユーザーは `Permission Denied` エラーを表示されることなくパスワードを変更できます。

setuid 権限は、次の例のように、ユーザーに `s` 権限を追加することでシンボリックに追加できます。

```shell
# chmod u+s suidexample.sh
```

setuid 権限は、次の例のように、権限セットの先頭に数字の 4 を付けることでも設定できます。

```shell
# chmod 4755 suidexample.sh
```

これで、`suidexample.sh` の権限は次のようになります。

```text
-rwsr-xr-x   1 trhodes  trhodes    63 Aug 29 06:36 suidexample.sh
```

ファイル所有者に対して指定された権限セットの一部として `s` が表示され、実行ビットが置き換えられていることに注意してください。
これにより、`man passwd(1)` のような、昇格した権限を必要とするユーティリティが実行できるようになります。

> **注:**
> `mount(8)` の `nosuid` オプションは、そのようなバイナリをユーザーに警告せずに静かに失敗させます。
> このオプションは、`nosuid` ラッパーがそれを回避できる可能性があるため、完全に信頼できるわけではありません。

これをリアルタイムで確認するには、2 つのターミナルを開きます。
一方のターミナルで、通常のユーザーとして `passwd` と入力します。
新しいパスワードの入力を待っている間に、プロセステーブルを確認して `man passwd(1)` のユーザー情報を見てください

`setgid` 権限付きで実行されると、プロセスを開始したユーザーではなく、ファイルを所有するグループに基づいた権限が付与されます。

ファイルに `setgid` 権限をシンボリックモードで設定するには、`man chmod(1)` を使用してグループに `s` 権限を追加します：

```shell
# chmod g+s sgidexample.sh
```

あるいは、`man chmod(1)` に先頭の 2 を指定します：

```shell
# chmod 2755 sgidexample.sh
```

次のリストでは、`s` がグループ権限設定用のフィールドに表示されていることに注目してください：

```shell
-rwxr-sr-x   1 trhodes  trhodes    44 Aug 31 01:49 sgidexample.sh
```

> **注:**
>
> これらの例では、対象のシェルスクリプトは実行可能ファイルですが、異なる EUID（実効ユーザー ID）で実行されることはありません。これは、シェルスクリプトが `man setuid(2)` システムコールにアクセスできないためです。

`setuid` および `setgid` 権限ビットは、権限を昇格させることにより、システムのセキュリティを低下させる可能性があります。3 つ目の特別な権限である `sticky bit`（スティッキービット）は、システムのセキュリティを強化できます。

`sticky bit` がディレクトリに設定されている場合、ファイルの削除はファイルの所有者のみに許可されます。これは、`/tmp` などのパブリックディレクトリにおいて、ファイルを所有していないユーザーによるファイル削除を防ぐのに役立ちます。この権限を利用するには、ファイルに `t` モードを追加します：

```shell
# chmod +t /tmp
```

あるいは、権限セットの先頭に 1 を付けます：

```shell
# chmod 1777 /tmp
```

`sticky bit` 権限は、権限セットの末尾に `t` として表示されます：

```shell
# ls -al / | grep tmp
```

```shell
drwxrwxrwt  10 root  wheel         512 Aug 31 01:49 tmp
```

## ディレクトリ構造

FreeBSD のディレクトリ階層は、システム全体を理解する上で基本となるものです。最も重要なディレクトリはルート（root）、すなわち `/` です。このディレクトリは起動時に最初にマウントされ、オペレーティングシステムをマルチユーザー運用に備えさせるために必要な基本システムを含んでいます。ルートディレクトリには、マルチユーザー運用への移行時にマウントされる他のファイルシステム用のマウントポイントも含まれています。

マウントポイントとは、追加のファイルシステムを親ファイルシステム（通常はルートファイルシステム）に接ぎ木できるディレクトリです。これについては、「ディスク構成（Disk Organization）」でさらに説明されています。

標準的なマウントポイントには、`/usr/`、`/var/`、`/tmp/`、`/mnt/`、`/media/` があります。これらのディレクトリは、通常 `/etc/fstab` のエントリに対応付けられています。このファイルは、さまざまなファイルシステムとマウントポイントの対応表であり、システムによって読み取られます。`/etc/fstab` 内のほとんどのファイルシステムは、そのエントリに `noauto` が含まれていない限り、起動時に `man rc(8)` スクリプトによって自動的にマウントされます。

## ディスク構成 (Disk Organization)

FreeBSD がファイルを検索するために使用する組織化の最小単位はファイル名です。
ファイル名は大文字と小文字を区別するため、`readme.txt` と `README.TXT` は別々のファイルになります。
FreeBSD はファイルの拡張子を使用して、ファイルがプログラム、ドキュメント、またはその他の形式のデータであるかを判断しません。

ファイルはディレクトリに格納されます。
ディレクトリにはファイルがまったく含まれないことも、数百のファイルが含まれることもあります。
ディレクトリは他のディレクトリを含むこともでき、データを整理するためにディレクトリを入れ子にした階層構造を構築できます。

ファイルとディレクトリを参照するには、ファイル名またはディレクトリ名の後にスラッシュ `/` を続け、さらに必要に応じて他のディレクトリ名を続けます。
たとえば、ディレクトリ `foo` がディレクトリ `bar` を含み、その `bar` がファイル `readme.txt` を含む場合、そのファイルの完全な名前、つまり _パス (path)_ は `foo/bar/readme.txt` です。
これは、ファイル名とディレクトリ名の区切りに `\` を使用する Windows(R) とは異なることに注意してください。
FreeBSD はパスにドライブ文字やその他のドライブ名を使用しません。
たとえば、FreeBSD では `c:\foo\bar\readme.txt` とは入力しません。

### ファイルシステム (File systems)

ディレクトリとファイルはファイルシステムに格納されます。
各ファイルシステムには、最上位レベルに正確に 1 つのディレクトリが含まれ、それはそのファイルシステムの _ルートディレクトリ (root directory)_ と呼ばれます。
このルートディレクトリは他のディレクトリを含むことができます。
1 つのファイルシステムが _ルートファイルシステム (root file system)_ または `/` として指定されます。
他のすべてのファイルシステムは、ルートファイルシステムの下に _マウント (mounted)_ されます。
FreeBSD システムに何枚のディスクがあっても、すべてのディレクトリは同じディスクの一部であるかのように見えます。

このディレクトリの内容を表示するために `man ls(1)` を使用すると、`A1` と `A2` という 2 つのサブディレクトリが表示されます。

## プロセスとデーモン

FreeBSD はマルチタスクオペレーティングシステムです。任意の時点で実行されている各プログラムは、_プロセス_ と呼ばれます。実行中のコマンドはそれぞれ少なくとも 1 つの新しいプロセスを開始し、FreeBSD によって実行される多数のシステムプロセスも存在します。

各プロセスは、_プロセス ID_（PID）と呼ばれる番号によって一意に識別されます。ファイルと同様に、各プロセスには所有者とグループがあり、所有者とグループの権限を使用して、プロセスが開くことができるファイルとデバイスが決定されます。ほとんどのプロセスには、それを開始した親プロセスも存在します。たとえば、シェルはプロセスであり、シェル内で開始された任意のコマンドは、シェルを親プロセスとして持つプロセスです。例外は、`init` と呼ばれる特別なプロセスです。これは起動時に常に最初に開始されるプロセスであり、常に PID が `1` です。

一部のプログラムは、継続的なユーザー入力を想定して設計されておらず、最初の機会に端末から切り離されます。たとえば、Web サーバーはユーザー入力ではなく Web リクエストに応答します。メールサーバーもこの種のアプリケーションのもう 1 つの例です。これらのタイプのプログラムは _デーモン_ として知られています。デーモンという用語はギリシャ神話に由来し、善でも悪でもなく、目に見えない形で有用なタスクを実行する存在を表します。そのため、BSD のマスコットは、スニーカーと熊手を持った陽気な顔のデーモンなのです。

通常デーモンとして実行されるプログラムの名前には、末尾に「d」を付けるという慣習があります。たとえば、BIND は Berkeley Internet Name Domain ですが、実際に実行されるプログラムは `named` です。Apache Web サーバープログラムは `httpd` であり、ラインプリンタスプーリングデーモンは `lpd` です。これは命名規則にすぎません。たとえば、Sendmail アプリケーションのメインメールデーモンは `sendmail` であり、`maild` ではありません。

### プロセスの表示

システム上で実行されているプロセスを確認するには、man:ps[1] または man:top[1] を使用します。現在実行中のプロセス、その PID、使用メモリ量、および開始時に使用されたコマンドの静的リストを表示するには、man:ps[1] を使用します。実行中のすべてのプロセスを表示し、数秒ごとに表示を更新して、コンピュータが何をしているのかを対話的に確認するには、man:top[1] を使用します。

デフォルトでは、man:ps[1] は、実行中でユーザーが所有するコマンドのみを表示します。次に例を示します。

```shell
% ps
```

出力は次のようになります。

```
 PID TT  STAT    TIME COMMAND
8203  0  Ss   0:00.59 /bin/csh
8895  0  R+   0:00.00 ps
```

man:ps[1] の出力は、いくつかの列に編成されています。`PID` 列はプロセス ID を表示します。PID は 1 から割り当てられ、99999 まで上がり、その後先頭に戻ります。ただし、すでに使用中の PID が再割り当てされることはありません。`TT` 列はプログラムが実行されている tty を表示し、`STAT` はプログラムの状態を表示します。`TIME` はプログラムが CPU 上で実行された時間です。これは通常、プログラムが開始されてからの経過時間ではありません。ほとんどのプログラムは、CPU 時間を必要とする前に、何かが起こるのを待つことに多くの時間を費やすためです。最後に、`COMMAND` はプログラムの開始に使用されたコマンドです。

表示される情報を変更するために、さまざまなオプションを利用できます。最も便利なセットの 1 つは `auxww` です。`a` はすべてのユーザーのすべての実行中プロセスに関する情報を表示し、`u` はプロセスの所有者のユーザー名とメモリ使用量を表示し、`x` はデーモンプロセスに関する情報を表示し、`ww` は man:ps[1] が、各プロセスのコマンドラインが画面に収まらなくなった時点で切り詰めるのではなく、完全なコマンドラインを表示するようにします。

man:top[1] の出力も同様です。

```shell
% top
```

出力は次のようになります。

```
last pid:  9609;  load averages:  0.56,  0.45,  0.36              up 0+00:20:03  10:21:46
107 processes: 2 running, 104 sleeping, 1 zombie
CPU:  6.2% user,  0.1% nice,  8.2% system,  0.4% interrupt, 85.1% idle
Mem: 541M Active, 450M Inact, 1333M Wired, 4064K Cache, 1498M Free
ARC: 992M Total, 377M MFU, 589M MRU, 250K Anon, 5280K Header, 21M Other
Swap: 2048M Total, 2048M Free

  PID USERNAME    THR PRI NICE   SIZE    RES STATE   C   TIME   WCPU COMMAND
  557 root          1 -21  r31   136M 42296K select  0   2:20  9.96% Xorg
 8198 dru           2  52    0   449M 82736K select  3   0:08  5.96% kdeinit4
 8311 dru          27  30    0  1150M   187M uwait   1   1:37  0.98% firefox
  431 root          1  20    0 14268K  1728K sel
```

出力は2つのセクションに分かれています。
ヘッダー（最初の5〜6行）には、最後に実行されたプロセスのPID、システムのロードアベレージ（システムがどの程度ビジーかを示す指標）、システムの稼働時間（前回の再起動からの経過時間）、現在時刻が表示されます。ヘッダーの他の数値は、実行中のプロセス数、使用されているメモリとスワップ容量、およびシステムが各CPU状態に費やしている時間に関連します。ZFSファイルシステムモジュールがロードされている場合、`ARC`行はディスクではなくメモリキャッシュから読み取られたデータ量を示します。

ヘッダーの下には、`man ps(1)`の出力と同様の情報を含む一連の列があります。たとえば、PID、ユーザー名、CPU時間、プロセスを起動したコマンドなどです。デフォルトでは、`man top(1)`はプロセスが使用しているメモリ容量も表示します。これは2つの列に分かれています。1つは合計サイズ、もう1つは常駐サイズです。合計サイズはアプリケーションが必要としたメモリ量で、常駐サイズは現在実際に使用しているメモリ量です。

`man top(1)`はデフォルトで2秒ごとに表示を自動更新します。別の間隔を指定するには`-s`を使用します。

[[basics-daemons]]
### プロセスの終了

実行中のプロセスまたはデーモンと通信する方法の1つは、`man kill(1)`を使用して_シグナル_を送信することです。シグナルにはさまざまな種類があります。特定の意味を持つものもあれば、アプリケーションのドキュメントで説明されているものもあります。ユーザーは自分が所有するプロセスにのみシグナルを送信でき、他の人のプロセスにシグナルを送信すると許可拒否エラーになります。例外は`root`ユーザーで、誰のプロセスにもシグナルを送信できます。

オペレーティングシステムもプロセスにシグナルを送信できます。アプリケーションの書き方が不適切で、アクセスすべきでないメモリにアクセスしようとした場合、FreeBSDはそのプロセスに「セグメンテーション違反」シグナル（`SIGSEGV`）を送信します。アプリケーションが一定時間経過後に通知を受けるように`man alarm(3)`システムコールを使用して作成されている場合、そのプロセスには「アラーム」シグナル（`SIGALRM`）が送信されます。

プロセスを停止するために使用できるシグナルは2つあります。`SIGTERM`と`SIGKILL`です。`SIGTERM`はプロセスを終了する丁寧な方法です。プロセスはシグナルを読み取り、開いているログファイルを閉じ、シャットダウンする前に実行中の処理を完了しようとすることができるためです。場合によっては、プロセスが中断できないタスクの途中である場合、`SIGTERM`を無視することがあります。

`SIGKILL`はプロセスが無視できません。プロセスに`SIGKILL`を送信すると、通常はその場でプロセスが停止します。 footnote:[中断できないタスクがいくつかあります。たとえば、プロセスがネットワーク上の別のコンピュータにあるファイルから読み取ろうとしており、そのコンピュータが利用できない場合、そのプロセスは「中断不能」であると言われます。最終的にはプロセスはタイムアウトします。通常は2分後です。このタイムアウトが発生するとすぐにプロセスは強制終了されます。]

他によく使用されるシグナルには、`SIGHUP`、`SIGUSR1`、`SIGUSR2`があります。これらは汎用シグナルであるため、アプリケーションによって応答が異なります。

たとえば、Webサーバーの設定ファイルを変更した後、Webサーバーに設定の再読み込みを指示する必要があります。`httpd`を再起動すると、Webサーバーで短時間の停止が発生します。代わりに、デーモンに`SIGHUP`シグナルを送信します。デーモンによって動作は異なるため、`SIGHUP`で目的の結果が得られるかどうかは、そのデーモンのドキュメントを参照してください。

> **重要**
>
> システム上のランダムなプロセスを強制終了することは賢明な行為ではありません。特に、`man init(8)`（PID 1）は特別です。`/bin/kill -s KILL 1`を実行すると、システムはすぐにシャットダウンしますが、これは推奨されません。kbd:[Return]を押す_前に_、`man kill(1)`の引数を_常に_再確認してください。

## シェル

*シェル* は、オペレーティングシステムと対話するためのコマンドラインインターフェースを提供します。シェルは入力チャネルからコマンドを受け取り、それを実行します。多くのシェルには、ファイル管理、ファイルグロビング、コマンドライン編集、コマンドマクロ、環境変数など、日常的な作業に役立つ組み込み機能があります。FreeBSD には、拡張 POSIX(R) シェル (man:sh[1]) や拡張 C シェル (man:tcsh[1]) など、いくつかのシェルが同梱されています。その他のシェルは FreeBSD Ports Collection から利用できます (`zsh` や `bash` など)。

使用するシェルは、実際には好みの問題です。C プログラマーは、man:tcsh[1] のような C 言語風のシェルに馴染みを感じるかもしれません。Linux(R) ユーザーは `bash` を好むかもしれません。各シェルには固有の特性があり、ユーザーの好みの作業環境に合う場合もあれば、合わない場合もあります。そのため、使用するシェルを選択できるようになっているのです。

シェルの一般的な機能のひとつに、ファイル名の補完があります。ユーザーがコマンド名やファイル名の最初の数文字を入力して kbd:[Tab] を押すと、シェルが残りのコマンド名やファイル名を補完します。ここに `foobar` と `football` という2つのファイルがあるとします。`foobar` を削除するには、`rm foo` と入力して kbd:[Tab] を押し、ファイル名を補完します。

しかし、シェルは `rm foo` と表示するだけです。`foobar` と `football` はどちらも `foo` で始まるため、ファイル名を補完できません。複数の名前が一致する場合、シェルによってはビープ音を鳴らしたり、選択肢をすべて表示したりします。ユーザーは、目的のファイル名を特定するために、さらに文字を入力する必要があります。`t` を入力してもう一度 kbd:[Tab] を押すと、シェルがどのファイル名が望まれているかを判断して、残りを補完するのに十分です。

シェルのもうひとつの機能は、環境変数の使用です。環境変数は、シェルの環境に格納された変数とキーのペアです。この環境は、シェルによって起動される任意のプログラムから読み取ることができるため、多くのプログラム設定が含まれています。一般的な環境変数とその意味の一覧は、[「共通環境変数」](#shell-env-vars) を参照してください。環境変数名は常に大文字であることに注意してください。

[[shell-env-vars]]
### 共通環境変数

| 変数 | 説明 |
|---|---|
| `USER` | 現在ログインしているユーザーの名前。 |
| `PATH` | バイナリを検索するディレクトリのコロン区切りリスト。 |
| `DISPLAY` | 接続先の Xorg ディスプレイのネットワーク名 (利用可能な場合)。 |
| `SHELL` | 現在のシェル。 |
| `TERM` | ユーザーの端末の種類の名前。端末の機能を決定するために使用される。 |
| `TERMCAP` | さまざまな端末機能を実行するための端末エスケープコードのデータベースエントリ。 |
| `OSTYPE` | オペレーティングシステムの種類。 |
| `MACHTYPE` | システムの CPU アーキテクチャ。 |
| `EDITOR` | ユーザーが好むテキストエディタ。 |
| `PAGER` | ユーザーがテキストを1ページずつ表示するために好んで使うユーティリティ。 |
| `MANPATH` | マニュアルページを検索するディレクトリのコロン区切りリスト。 |

環境変数の設定方法は、シェルによって異なります。man:tcsh[1] と man:csh[1] では、環境変数を設定するために `setenv` を使用します。man:sh[1] と `bash` では、現在の環境変数を設定するために `export` を使用します。次の例では、man:tcsh[1] シェルのデフォルトの `EDITOR` を `/usr/local/bin/emacs` に設定しています。

```shell
% setenv EDITOR /usr/local/bin/emacs
```

`bash` での同等のコマンドは次のとおりです。

```shell
% export EDITOR="/usr/local/bin/emacs"
```

環境変数を展開して現在の設定を確認するには、コマンドラインでその名前の前に `$` 文字を入力します。たとえば、`echo $TERM` は現在の `$TERM` 設定を表示します。

シェルは、メタキャラクターと呼ばれる特殊文字を、データの特別な表現として扱います。最も一般的なメタキャラクターは `\*` で、ファイル名の任意の数の文字を表します。メタキャラクターはファイル名グロビングを実行するために使用できます。たとえば、`echo *` は `ls` と同等です。これは、シェルが `*` に一致するすべてのファイルを受け取り、`echo` がそれらをコマンドラインにリストアップするためです。

シェルが特殊文字を解釈しないようにするには、バックスラッシュ (`\`) を前に付けてシェルからエスケープします。たとえば、`echo $TERM` は端末設定を表示しますが、`echo \$TERM` は文字列 `$TERM` を文字通り表示します。

[[changing-shells]]
### シェルの変更

デフォルトのシェルを恒久的に変更する最も簡単な方法は、`chsh` を使用することです。このコマンドを実行すると、`EDITOR` 環境変数で設定されているエディタ (デフォルトでは man:vi[1] に設定されています) が開きます。`Shell:` の行をフルパスに変更します。

新しいシェル。

あるいは、`chsh -s` を使用すると、エディタを開かずに指定したシェルを設定できます。
例えば、シェルを `bash` に変更するには：

```shell
% chsh -s /usr/local/bin/bash
```

プロンプトでパスワードを入力し、<kbd>Return</kbd> を押してシェルを変更します。
ログオフしてから再度ログインすると、新しいシェルを使い始めることができます。

> **注:**
> 新しいシェルは `/etc/shells` に存在していなければなりません。
> シェルが FreeBSD Ports Collection（「Installing Applications: Packages and Ports」を参照）からインストールされた場合は、このファイルに自動的に追加されているはずです。
> 存在しない場合は、パスをシェルのパスに置き換えて、次のコマンドで追加してください。
>
> ```shell
> # echo /usr/local/bin/bash >> /etc/shells
> ```
>
> その後、`man chsh(1)` を再実行してください。

### 高度なシェルテクニック

UNIX(R) シェルは単なるコマンドインタープリタではなく、ユーザーがコマンドを実行し、出力をリダイレクトし、入力をリダイレクトし、コマンドをチェーンして最終的なコマンド出力を改善することを可能にする強力なツールとして機能します。
この機能が組み込みコマンドと組み合わされると、ユーザーは効率を最大限に高めることのできる環境を得られます。

シェルのリダイレクトは、コマンドの出力または入力を別のコマンドやファイルに送る操作です。
例えば、`man ls(1)` コマンドの出力をファイルに取り込むには、出力をリダイレクトします：

```shell
% ls > directory_listing.txt
```

これで、ディレクトリの内容が `directory_listing.txt` にリストされます。
`man sort(1)` のように、入力を読み取るために使用できるコマンドもあります。
このリストを並べ替えるには、入力をリダイレクトします：

```shell
% sort < directory_listing.txt
```

入力は並べ替えられて画面に表示されます。
その入力を別のファイルにリダイレクトするには、方向を混在させて `man sort(1)` の出力をリダイレクトします：

```shell
% sort < directory_listing.txt > sorted.txt
```

これまでのすべての例では、コマンドはファイル記述子を使用してリダイレクトを実行しています。
すべての UNIX(R) システムにはファイル記述子があり、これには標準入力 (stdin)、標準出力 (stdout)、標準エラー (stderr) が含まれます。
それぞれに目的があり、入力はキーボードやマウスなど、入力を提供するものになります。
出力は画面やプリンタの紙などです。
エラーは、診断メッセージやエラーメッセージに使用されるものすべてです。
この 3 つはすべて I/O ベースのファイル記述子と見なされ、ストリームと見なされることもあります。

これらの記述子を使用することで、シェルは出力と入力がさまざまなコマンド間で受け渡され、ファイルへ、またはファイルからリダイレクトされることを可能にします。
リダイレクトのもう 1 つの方法はパイプ演算子です。

UNIX(R) のパイプ演算子 "|" は、あるコマンドの出力を別のプログラムに直接渡したり、向けたりすることを可能にします。
基本的に、パイプはコマンドの標準出力を別のコマンドの標準入力として渡すことを可能にします。例えば：

```shell
% cat directory_listing.txt | sort | less
```

この例では、`directory_listing.txt` の内容が並べ替えられ、その出力が `man less(1)` に渡されます。
これにより、ユーザーは自分のペースで出力をスクロールし、出力が画面からスクロールして消えるのを防ぐことができます。
