# 第19章 必須アクセス制御（Mandatory Access Control）

本章では、FreeBSDのMACフレームワークと、さまざまなセキュリティ機構を有効にするための差し替え可能なセキュリティポリシーモジュールを説明します。例に出てくる設定は仕組みを理解するためのもので、そのまま本番環境へ適用するものではありません。

<a id="mac-synopsis"></a>
## 概要

FreeBSDは、POSIX.1eドラフトに基づくセキュリティ拡張に対応しています。その代表が、ファイルシステムのアクセス制御リスト（ACL。[「アクセス制御リスト」の節](https://docs.freebsd.org/en/books/handbook/security/#fs-acl)を参照）と、必須アクセス制御（Mandatory Access Control、MAC）です。MACでは、アクセス制御モジュールを読み込んでセキュリティポリシーを実現します。モジュールには、システムのごく一部、たとえば特定のサービスだけを堅牢にするものもあれば、すべての主体（subject）と客体（object）にラベルを付けて包括的に保護するものもあります。

「必須（mandatory）」とは、制御を強制するのが利用者ではなく、管理者とオペレーティングシステムだという意味です。標準の裁量アクセス制御（Discretionary Access Control、DAC）では、アクセス権をどう設定するかを利用者の裁量に任せているので、この点が対照的です。

本章では、MACフレームワークと、FreeBSDが提供するポリシーモジュール群の使い方を中心に説明します。

本章で学ぶ内容は次のとおりです。

* MACフレームワークに関する用語
* MACポリシーモジュールの機能と、ラベルを使うポリシーと使わないポリシーの違い
* MACフレームワークを使うようにシステムを設定する前に検討すべきこと
* FreeBSDに含まれるMACポリシーモジュールと、その設定方法
* MACフレームワークでより安全な環境を作る方法
* MACの設定が正しく働いているかを確かめる方法

本章を読む前に、次の知識が必要です。

* UNIXとFreeBSDの基本を理解していること（[FreeBSDの基本](03-basics.md#basics)）
* セキュリティと、それがFreeBSDにどう関わるかをある程度知っていること（[セキュリティ](https://docs.freebsd.org/en/books/handbook/security/#security)）

> **警告**: MACの設定を誤ると、システムにアクセスできなくなったり、利用者に不便を強いたり、Xorgの機能が使えなくなったりすることがあります。さらに重要なのは、MACだけでシステムが完全に守られると考えてはいけないという点です。MACフレームワークは、既存のセキュリティポリシーを補強するものにすぎません。確かなセキュリティ運用と定期的な点検がなければ、システムが完全に安全になることはありません。
>
> 本章の例は説明用です。例の設定を本番システムへ適用してはいけません。どんなセキュリティポリシーでも、導入には十分な理解と適切な設計、徹底したテストが欠かせません。

本章はMACフレームワークに関わるセキュリティの問題を幅広く扱いますが、新しいMACセキュリティポリシーモジュールの開発は対象外です。MACフレームワークには、テストや新規モジュール開発のための特殊な性質を持つモジュールも含まれています。これらについては `mac_test(4)`、`mac_stub(4)`、`mac_none(4)` を参照してください。

<a id="mac-inline-glossary"></a>
## 主要な用語

MACフレームワークでは、次の用語を使います。

* *compartment*（コンパートメント）: 分割・隔離されるプログラムとデータの集合です。利用者には、システムの特定の構成要素へのアクセスだけを明示的に与えます。作業グループ、部門、プロジェクト、話題などのまとまりを表し、「知る必要のある人にだけ知らせる」（need-to-know）方針のポリシーを実現できます。
* *integrity*（完全性）: データをどこまで信頼できるかの度合いです。データの完全性が高いほど、そのデータを信頼できます。
* *level*（レベル）: セキュリティ属性の値の高低です。レベルが上がると、安全性も高いとみなされます。
* *label*（ラベル）: ファイル、ディレクトリなど、システム内のさまざまな対象に付けられるセキュリティ属性で、機密性の印のようなものです。ファイルにラベルを付けると、そのファイルのセキュリティ上の性質を表し、同等のセキュリティ設定を持つファイル、利用者、リソースだけにアクセスを許します。ラベルの値の意味や解釈はポリシーの設定次第です。ラベルを対象の完全性や機密度を表すものとして扱うポリシーもあれば、アクセス規則を保持するために使うポリシーもあります。
* *multilabel*（マルチラベル）: ファイルシステムのオプションの一つです。シングルユーザーモードで `tunefs(8)` を使うか、起動時に `fstab(5)` で、あるいはファイルシステムの新規作成時に設定できます。これを有効にすると、管理者は対象ごとに異なるMACラベルを付けられます。ラベルに対応したセキュリティポリシーモジュールにだけ関係します。
* *single label*（シングルラベル）: ファイルシステム全体で一つのラベルを使い、データの流れのアクセス制御を行うポリシーです。`multilabel` を設定していなければ、すべてのファイルが同じラベル設定に従います。
* *object*（客体）: *subject* の指示に従って情報が流れる実体です。ディレクトリ、ファイル、フィールド、画面、キーボード、メモリ、磁気記憶装置、プリンターなど、データを蓄えたり運んだりするあらゆる装置が含まれます。客体はデータの入れ物であり、システムリソースです。客体へのアクセスは、実質的にそのデータへのアクセスを意味します。
* *subject*（主体）: 利用者、利用者のプロセス、システムのプロセスなど、*object* の間で情報を流す能動的な実体です。FreeBSDでは、ほとんどの場合、利用者に代わってプロセス内で動くスレッドを指します。
* *policy*（ポリシー）: 目標をどう達成するかを定める規則の集まりです。通常は、特定の対象をどのように扱うかを文書化したものです。本章では、データと情報の流れを制御し、誰がそれらにアクセスできるかを定める規則の集まりを指します。
* *high-watermark*（ハイウォーターマーク）: より高いレベルの情報にアクセスするために、セキュリティレベルを引き上げることを認めるポリシーです。多くの場合、処理が終わると元のレベルに戻ります。現在のFreeBSDのMACフレームワークには、この種のポリシーは含まれていません。
* *low-watermark*（ローウォーターマーク）: 安全性の低い情報にアクセスするために、セキュリティレベルを引き下げることを認めるポリシーです。多くの場合、処理が終わると利用者の元のセキュリティレベルに戻ります。FreeBSDでこれを使うセキュリティポリシーモジュールは `mac_lomac(4)` だけです。
* *sensitivity*（機密度）: 主にマルチレベルセキュリティ（Multilevel Security、MLS）の話題で使います。機密度のレベルは、そのデータがどれほど重要か、秘密にすべきかを表します。機密度が上がるほど、データの秘匿性、つまり機密性の重要度も上がります。

<a id="mac-understandlabel"></a>
## MACラベルを理解する

MACラベルは、システム内の主体と客体に付けられるセキュリティ属性です。ラベルを設定するときは、システムが思わぬ動作をしないよう、その影響を管理者が理解している必要があります。客体で使える属性は、読み込まれているポリシーモジュールによって決まります。モジュールごとに属性の解釈が異なるからです。

客体のセキュリティラベルは、ポリシーがアクセス可否を判断するときの材料の一部になります。ポリシーによっては、ラベルだけで判断に必要な情報がすべてそろいます。別のポリシーでは、ラベルは、より大きな規則群の一部として処理されます。

ラベルのポリシーには、シングルラベルとマルチラベルの2種類があります。既定ではシングルラベルが使われます。システムのセキュリティモデルの要件に合うポリシーを実現するには、それぞれの長所と短所を管理者が知っておく必要があります。

シングルラベルのセキュリティポリシーでは、すべての主体と客体に一つのラベルしか使えません。システム全体に一組のアクセス権限を強制するため、管理の手間は少なくて済みますが、ラベルに対応したポリシーの柔軟性は下がります。それでも、多くの環境ではシングルラベルのポリシーで十分です。

シングルラベルのポリシーは、DACとやや似ています。`root` がポリシーを設定し、利用者を適切なカテゴリとアクセスレベルに振り分けるからです。大きな違いは、多くのポリシーモジュールが `root` も制限できることです。客体に対する基本的な制御はグループに委ねられますが、`root` はいつでもその設定を取り消したり変更したりできます。

必要に応じて、UFSファイルシステムに `tunefs(8)` で `multilabel` を指定すると、マルチラベルのポリシーを使えます。マルチラベルのポリシーでは、主体と客体のそれぞれに独立したMACラベルを持たせられます。マルチラベルかシングルラベルかを選ぶ必要があるのは、`biba`、`lomac`、`mls` のようにラベル機能を実装したポリシーだけです。`seeotheruids`、`portacl`、`partition` のように、ラベルをまったく使わないポリシーもあります。

パーティションにマルチラベルのポリシーを使い、マルチラベルのセキュリティモデルを構築すると、そのファイルシステム内のすべてにラベルが付くため、管理の手間が増えます。ディレクトリやファイルはもちろん、デバイスノードにもラベルが付きます。

次のコマンドは、指定したUFSファイルシステムに `multilabel` を設定します。これはシングルユーザーモードでしか実行できません。スワップのファイルシステムには必要ありません。

```shell
# tunefs -l enable /
```

> **注意**: ルートパーティションに `multilabel` フラグを設定すると、問題が起きたという報告があります。そのような場合は、[MACフレームワークのトラブルシューティング](#mac-troubleshoot)を確認してください。

マルチラベルのポリシーはファイルシステム単位で設定するので、ファイルシステムの構成をよく設計すれば、マルチラベルが不要になることもあります。FreeBSDのWebサーバーでのMACセキュリティモデルを例に考えてみましょう。このマシンでは、既定のファイルシステムのすべてに、`biba/high` というシングルラベルを使います。書き込みを上位へ及ぼせないようにするため、Webサーバーを `biba/low` で動かす必要があるなら、`biba/low` に設定した別のUFSファイルシステム `/usr/local` にインストールすればよいのです。

<a id="chapter-19-heading-05"></a>
### ラベルの設定

ラベルポリシーモジュールの設定は、ほぼすべて基本システムのユーティリティで行います。これらのコマンドは、客体や主体の設定、設定内容の操作と検証のための簡単なインターフェイスを提供します。

設定はすべて `setfmac` と `setpmac` で行えます。`setfmac` はシステム上の客体にMACラベルを設定し、`setpmac` は主体にラベルを設定します。たとえば、`test` に `biba` のMACラベル `high` を設定するには次のようにします。

```shell
# setfmac biba/high test
```

設定が成功すれば、エラーなくプロンプトに戻ります。よくあるエラーは `Permission denied` で、制限された客体のラベルを設定・変更しようとしたときに起こるのが普通です。ほかの条件でも別の失敗が起こりえます。たとえば、再ラベルしようとする利用者がそのファイルの所有者でない場合、客体が存在しない場合、客体が読み取り専用の場合などです。必須ポリシーは、ファイルの性質、プロセスの性質、新しいラベル値の性質などを理由に、プロセスによるファイルの再ラベルを許可しないことがあります。たとえば、低い完全性で動く利用者が高い完全性のファイルのラベルを変更しようとしたり、低い完全性のファイルのラベルを高い完全性のラベルに変更しようとしたりすると、これらの操作は失敗します。

システム管理者は `setpmac` を使うと、起動するプロセスに別のラベルを割り当てて、ポリシーモジュールの設定を上書きできます。

```shell
# setfmac biba/high test
Permission denied
# setpmac biba/low setfmac biba/high test
# getfmac test
test: biba/high
```

sendmailのように実行中のプロセスには、通常 `getpmac` を使います。このコマンドは、コマンド名の代わりにプロセスID（PID）を受け取ります。読み込まれているポリシーモジュールの規則により、利用者が自分のアクセス権の及ばないファイルを操作しようとすると、`Operation not permitted` エラーが表示されます。

<a id="chapter-19-heading-06"></a>
### 定義済みのラベル

ラベル機能に対応したFreeBSDのポリシーモジュールの一部は、`low`、`equal`、`high` という3つの定義済みラベルを提供します。それぞれの意味は次のとおりです。

* `low` は、客体や主体が持てる最も低いラベル設定です。客体や主体にこれを設定すると、high に設定された客体や主体へのアクセスが阻止されます。
* `equal` は、主体や客体を無効、つまり影響を受けない状態にします。ポリシーの適用除外とみなす客体にだけ設定してください。
* `high` は、BibaおよびMLSのポリシーモジュールで使える最高の設定を、客体や主体に与えます。

これに該当するポリシーモジュールは、`mac_biba(4)`、`mac_mls(4)`、`mac_lomac(4)` です。定義済みラベルは、それぞれ異なる情報フローの指針を確立します。汎用ラベルの設定がどのような特性を持つかは、各モジュールのマニュアルページで確認してください。

<a id="chapter-19-heading-07"></a>
### 数値ラベル

BibaおよびMLSのポリシーモジュールは数値ラベルに対応しており、階層的な制御の正確なレベルを指定できます。この数値のレベルは、情報を分類のグループに分けたり並べたりするために使い、そのグループ以上のグループレベルにだけアクセスを許します。たとえば、次のように書きます。

```
biba/10:2+3+6(5:2+3-20:2+3+4+5+6)
```

これは「Bibaポリシーのラベル／グレード10：コンパートメント2、3、6：（グレード5……」のように解釈できます。

この例では、最初のグレードが有効グレード（有効なコンパートメント付き）、2番目のグレードが下限グレード、最後のものが上限グレードです。ほとんどの構成では、このような細かい設定は高度な構成とみなされ、必要ありません。

システム上の客体が持つのは、現在のグレードとコンパートメントだけです。システム上の主体は、システムで使える権限の範囲を反映します。アクセス制御に使われる場合は、ネットワークインターフェイスも同様です。

主体と客体の組のグレードとコンパートメントから、*支配*（dominance）という関係が決まります。主体が客体を支配する場合、客体が主体を支配する場合、どちらも他方を支配しない場合、互いに支配する場合があります。「互いに支配する」のは、2つのラベルが等しいときです。Bibaは情報フローの性質上、利用者がプロジェクトに対応するようなコンパートメントの集合に対する権利を持ち、客体も同様にコンパートメントの集合を持ちます。制限されていないコンパートメントにある客体へアクセスするには、利用者が `su` や `setpmac` を使って、自分の権利を絞り込む必要があるかもしれません。

<a id="chapter-19-heading-08"></a>
### 利用者ラベル

利用者のファイルとプロセスがシステムのセキュリティポリシーと正しくやり取りするためには、利用者にラベルが必要です。これは `/etc/login.conf` でログインクラスを使って設定します。ラベルを使うポリシーモジュールはすべて、利用者クラスの設定を実装しています。

MACで強制される利用者クラスの既定ラベルを設定するには、`label` エントリを追加します。次に、すべてのポリシーモジュールを含む `label` エントリの例を示します。実際の設定で、すべてのポリシーモジュールを有効にすることは決してありません。何かを設定する前に、本章の残りの部分を読んでおくことを勧めます。

```
default:\
	:welcome=/etc/motd:\
	:setenv=MAIL=/var/mail/$,BLOCKSIZE=K:\
	:path=~/bin:/sbin:/bin:/usr/sbin:/usr/bin:/usr/local/sbin:/usr/local/bin:\
	:manpath=/usr/share/man /usr/local/man:\
	:nologin=/usr/sbin/nologin:\
	:cputime=1h30m:\
	:datasize=8M:\
	:vmemoryuse=100M:\
	:stacksize=2M:\
	:memorylocked=4M:\
	:memoryuse=8M:\
	:filesize=8M:\
	:coredumpsize=8M:\
	:openfiles=24:\
	:maxproc=32:\
	:priority=0:\
	:requirehome:\
	:passwordtime=91d:\
	:umask=022:\
	:ignoretime@:\
	:label=partition/13,mls/5,biba/10(5-15),lomac/10[2]:
```

利用者は既定値を変更できませんが、ログイン後に、ポリシーの制約の範囲内で自分のラベルを変更できます。上の例は、Bibaポリシーに対して、プロセスの最小の完全性が `5`、最大が `15`、既定の有効ラベルが `10` であることを伝えています。プロセスは、ラベルを変更するまで `10` で動作します。たとえば利用者が `setpmac` を使うと変更できますが、Bibaによって設定された範囲内に制限されます。

`login.conf` を変更したら、`cap_mkdb` でログインクラスの機能データベースを作り直す必要があります。

多くのサイトでは、多数の利用者がいて、いくつもの異なる利用者クラスが必要になります。これは管理が難しくなりかねないので、綿密な計画が必要です。

<a id="chapter-19-heading-09"></a>
### ネットワークインターフェイスのラベル

ネットワークインターフェイスにもラベルを設定でき、ネットワーク上のデータの流れを制御するのに役立ちます。ネットワークインターフェイスのラベルを使うポリシーは、客体に対するポリシーと同じように働きます。たとえば、Bibaで高い設定にある利用者は、ラベルが `low` のネットワークインターフェイスへのアクセスを許されません。

ネットワークインターフェイスにMACラベルを設定するときは、`ifconfig` に `maclabel` を渡します。

```shell
# ifconfig bge0 maclabel biba/equal
```

この例は、`bge0` インターフェイスにMACラベル `biba/equal` を設定します。`biba/high(low-high)` のような設定を使うときは、エラーにならないよう、ラベル全体を引用符で囲んでください。

ラベルに対応した各ポリシーモジュールには、ネットワークインターフェイスのMACラベルを無効にするための調整項目（tunable）があります。ラベルを `equal` に設定しても、似た効果が得られます。これらの調整項目について詳しくは、`sysctl` の出力、各ポリシーのマニュアルページ、本章の残りの説明を確認してください。

<a id="mac-planning"></a>
## セキュリティ設定の計画

MACポリシーを導入する前に、計画の段階を設けることを勧めます。計画では、管理者が次のような導入の要件と目標を検討します。

* 対象システムの情報とリソースをどのように分類するか。
* どの情報やリソースへのアクセスを制限するか、またどんな種類の制限を課すか。
* この目標を達成するには、どのMACモジュールが必要か。

信頼されたシステムとその設定の試験運用は、MACを本番システムで使い始める*前に*行ってください。環境によって必要なものや要件は異なるため、あらかじめセキュリティプロファイルを完全に決めておけば、運用開始後の変更を減らせます。

MACフレームワークがシステム全体のセキュリティをどう強化するかを考えてください。MACフレームワークが提供するさまざまなセキュリティポリシーモジュールは、ネットワークやファイルシステムの保護、特定のポートやソケットへの利用者のアクセスの阻止に使えます。おそらく、ポリシーモジュールの最善の使い方は、複数のセキュリティポリシーモジュールを同時に読み込んで、MLS環境を作ることでしょう。この方法は、特定の目的にだけ使うシステムの要素を堅牢にする、いわゆるハードニングのポリシーとは異なります。MLSの欠点は、管理の手間が増えることです。

ただし、特定の構成に必要なポリシーを選んで使える柔軟性を持ち、性能面の負荷も抑えられるフレームワークが長く効果を発揮することを考えれば、その手間は小さなものです。不要なポリシーへの対応を減らせば、システム全体の性能が上がり、選択の柔軟性も高まります。優れた導入とは、全体のセキュリティ要件を考慮したうえで、フレームワークが提供するさまざまなセキュリティポリシーモジュールを効果的に実装することです。

MACを使うシステムでは、利用者が自分の意思でセキュリティ属性を変更できないことが保証されます。利用者向けのユーティリティ、プログラム、スクリプトはすべて、選択したセキュリティポリシーモジュールが定めるアクセス規則の制約内で動作しなければなりません。MACのアクセス規則の管理は、システム管理者の手の中にあります。

適切なセキュリティポリシーモジュールを慎重に選ぶのは、システム管理者の責務です。ネットワーク越しのアクセス制御を制限する必要がある環境では、`mac_portacl(4)`、`mac_ifoff(4)`、`mac_biba(4)` の各ポリシーモジュールが出発点として適しています。ファイルシステムの客体の厳格な機密性が必要な環境では、`mac_bsdextended(4)` と `mac_mls(4)` のポリシーモジュールを検討してください。

ネットワークの構成に基づいて、ポリシーを決めることもできます。特定の利用者にだけ `ssh(1)` へのアクセスを許したいなら、`mac_portacl(4)` ポリシーモジュールが向いています。ファイルシステムの場合は、ある利用者にとって機密である客体が、別の利用者にとってはそうでないということがあります。たとえば、大きな開発チームがいくつかの小さなプロジェクトに分かれていて、プロジェクトAの開発者が、プロジェクトBの開発者が書いた客体にアクセスできないようにしたいとします。それでいて、両方のプロジェクトが、プロジェクトCの開発者が作った客体にアクセスする必要があるかもしれません。MACフレームワークの各セキュリティポリシーモジュールを使えば、利用者をこうしたグループに分け、それぞれに適切な客体へのアクセスを与えられます。

セキュリティポリシーモジュールは、それぞれ独自の方法でシステム全体のセキュリティを扱います。モジュールの選択は、十分に検討したセキュリティポリシーに基づくべきです。そのポリシーは、見直しと再実装が必要になることもあります。MACフレームワークの各セキュリティポリシーモジュールを理解しておくと、管理者は自分の状況に最適なポリシーを選びやすくなります。

本章の残りでは、利用できるモジュールを取り上げ、その使い方と設定を説明します。状況によっては、適用が考えられる場面についての洞察も示します。

> **注意**: MACの導入は、ファイアウォールの導入によく似ています。システムから完全に締め出されないよう、注意が必要です。以前の設定へ戻す手段を用意しておくべきです。リモート接続越しにMACを導入するときは、細心の注意を払ってください。

<a id="mac-policies"></a>
## 利用できるMACポリシー

FreeBSDの既定のカーネルには `options MAC` が含まれています。つまり、MACフレームワークに含まれるすべてのモジュールを、実行時のカーネルモジュールとして `kldload` で読み込めます。モジュールをテストしたら、起動時に読み込まれるよう、モジュール名を `/boot/loader.conf` に追加してください。独自のカーネルをコンパイルする管理者向けに、各モジュールにはカーネルオプションも用意されています。

FreeBSDには、ほとんどのセキュリティ要件をカバーするポリシー群が含まれています。以下に、各ポリシーの概要を示します。最後の3つのポリシーは、3つの既定ラベルの代わりに整数の設定にも対応します。

<a id="mac-seeotheruids"></a>
### MAC See Other UIDsポリシー

モジュール名: `mac_seeotheruids.ko`

カーネル設定行: `options MAC_SEEOTHERUIDS`

起動オプション: `mac_seeotheruids_load="YES"`

`mac_seeotheruids(4)` モジュールは、`security.bsd.see_other_uids` と `security.bsd.see_other_gids` の `sysctl` 調整項目を拡張します。このオプションは、設定の前にラベルを設定しておく必要がなく、ほかのモジュールとも支障なく共存できます。

モジュールを読み込んだら、次の `sysctl` 調整項目で機能を制御できます。

* `security.mac.seeotheruids.enabled` はモジュールを有効にし、既定の設定を適用します。既定では、他の利用者が所有するプロセスやソケットを、利用者が見られないようにします。
* `security.mac.seeotheruids.specificgid_enabled` は、指定したグループをこのポリシーの適用から除外します。特定のグループを除外するには、`security.mac.seeotheruids.specificgid=XXX` という `sysctl` 調整項目を使い、*XXX* を除外したいグループの数値IDに置き換えます。
* `security.mac.seeotheruids.primarygroup_enabled` は、特定のプライマリグループをこのポリシーから除外するために使います。この調整項目を使うときは、`security.mac.seeotheruids.specificgid_enabled` を設定してはいけません。

<a id="mac-bsdextended"></a>
### MAC BSD Extendedポリシー

モジュール名: `mac_bsdextended.ko`

カーネル設定行: `options MAC_BSDEXTENDED`

起動オプション: `mac_bsdextended_load="YES"`

`mac_bsdextended(4)` モジュールは、ファイルシステムのファイアウォールを実現します。標準のファイルシステムの権限モデルを拡張し、ファイルシステム階層内のファイル、ユーティリティ、ディレクトリを保護するための、ファイアウォールに似た規則集合を管理者が作れるようにします。ファイルシステムの客体にアクセスしようとすると、一致する規則が見つかるか、規則の末尾に達するまで、規則の一覧を順に調べます。この動作は `security.mac.bsdextended.firstmatch_enabled` で変更できます。FreeBSDのほかのファイアウォール系モジュールと同様に、アクセス制御規則を書いたファイルを作っておき、`rc.conf(5)` の変数を使って起動時にシステムに読み込ませることもできます。

規則の一覧は `ugidfw(8)` で入力できます。構文は `ipfw(8)` に似ています。`libugidfw(3)` ライブラリの関数を使えば、さらにツールを書けます。

`mac_bsdextended(4)` モジュールを読み込んだら、次のコマンドで現在の規則設定を一覧表示できます。

```shell
# ugidfw list
0 slots, 0 rules
```

既定では規則は何も定義されておらず、すべてに自由にアクセスできます。`root` には影響を与えず、利用者によるすべてのアクセスを阻止する規則を作るには、次のようにします。

```shell
# ugidfw add subject not uid root new object not uid root mode n
```

この規則は簡単に実装できますが、すべての利用者があらゆるコマンドを実行できなくなるので、非常に悪い考えです。より現実的な例として、`user1` が `user2` のホームディレクトリにアクセスすることを、ディレクトリの一覧表示も含めてすべて阻止する規則を次に示します。

```shell
# ugidfw set 2 subject uid user1 object uid user2 mode n
# ugidfw set 3 subject uid user1 object gid user2 mode n
```

`user1` の代わりに `not uid user2` を使えば、すべての利用者に同じアクセス制限を課せます。ただし、`root` はこれらの規則の影響を受けません。

> **注意**: このモジュールを使うときは、細心の注意が必要です。誤った使い方をすると、ファイルシステムの一部にアクセスできなくなるおそれがあります。

<a id="mac-ifoff"></a>
### MAC Interface Silencingポリシー

モジュール名: `mac_ifoff.ko`

カーネル設定行: `options MAC_IFOFF`

起動オプション: `mac_ifoff_load="YES"`

`mac_ifoff(4)` モジュールは、ネットワークインターフェイスを動作中に無効にしたり、システムの起動時にネットワークインターフェイスが立ち上がらないようにしたりするために使います。ラベルは使わず、ほかのMACモジュールにも依存しません。

このモジュールの制御は、ほとんどが次の `sysctl` 調整項目で行います。

* `security.mac.ifoff.lo_enabled` は、ループバックインターフェイス `lo(4)` のすべての通信を有効または無効にします。
* `security.mac.ifoff.bpfrecv_enabled` は、Berkeley Packet Filterインターフェイス `bpf(4)` のすべての通信を有効または無効にします。
* `security.mac.ifoff.other_enabled` は、そのほかのすべてのインターフェイスの通信を有効または無効にします。

`mac_ifoff(4)` の最も一般的な使い方の一つは、起動の手順の間はネットワーク通信を許可したくない環境での、ネットワーク監視です。別の使い方として、`security/aide` のようなアプリケーションを使うスクリプトを書き、保護対象のディレクトリに新しいファイルや変更されたファイルを見つけたら、自動的にネットワーク通信を遮断するという方法もあります。

<a id="mac-portacl"></a>
### MAC Port Access Control Listポリシー

モジュール名: `mac_portacl.ko`

カーネル設定行: `MAC_PORTACL`

起動オプション: `mac_portacl_load="YES"`

> **訳注**: ほかのモジュールの説明では「カーネル設定行」が `options MAC_...` の形ですが、固定原文のこのモジュールだけ `options` が付いていません。FreeBSD 15.1の [mac_portacl(4)](https://man.freebsd.org/cgi/man.cgi?query=mac_portacl&sektion=4) では、カーネル設定ファイルの記述は `options MAC_PORTACL` です。原文の記述はそのまま残しています。

`mac_portacl(4)` モジュールは、ローカルのTCPおよびUDPポートへのバインドを制限するために使います。これにより、`root` 以外の利用者にも、1024未満の特権ポートのうち指定したものへのバインドを許せます。

読み込むと、このモジュールはすべてのソケットでMACポリシーを有効にします。次の調整項目が使えます。

* `security.mac.portacl.enabled` は、ポリシーを完全に有効または無効にします。
* `security.mac.portacl.port_high` は、`mac_portacl(4)` が保護する最大のポート番号を設定します。
* `security.mac.portacl.suser_exempt` は、0以外の値に設定すると、`root` をこのポリシーの適用から除外します。
* `security.mac.portacl.rules` は、ポリシーを `rule[,rule,...]` の形式の文字列で指定します。規則は必要な数だけ書け、各規則の形式は `idtype:id:protocol:port` です。`idtype` は `uid` か `gid` のどちらかです。`protocol` には `tcp` または `udp` を指定できます。`port` は、指定した利用者またはグループがバインドを許されるポート番号です。利用者ID、グループID、ポートには、数値だけを使えます。

既定では、1024未満のポートを使えるのは、`root` として動く特権プロセスだけです。`mac_portacl(4)` によって、特権のないプロセスが1024未満のポートにバインドできるようにするには、次の調整項目を設定します。

```shell
# sysctl security.mac.portacl.port_high=1023
# sysctl net.inet.ip.portrange.reservedlow=0
# sysctl net.inet.ip.portrange.reservedhigh=0
```

このポリシーが `root` に影響しないようにするには、`security.mac.portacl.suser_exempt` を0以外の値に設定します。

```shell
# sysctl security.mac.portacl.suser_exempt=1
```

UID 80の `www` 利用者が、`root` 権限なしでポート80にバインドできるようにするには、次のようにします。

```shell
# sysctl security.mac.portacl.rules=uid:80:tcp:80
```

次の例は、UIDが1001の利用者に、TCPポート110（POP3）と995（POP3s）へのバインドを許可します。

```shell
# sysctl security.mac.portacl.rules=uid:1001:tcp:110,uid:1001:tcp:995
```

<a id="mac-partition"></a>
### MAC Partitionポリシー

モジュール名: `mac_partition.ko`

カーネル設定行: `options MAC_PARTITION`

起動オプション: `mac_partition_load="YES"`

`mac_partition(4)` ポリシーは、プロセスをMACラベルに基づいて特定の「パーティション」に入れます。このポリシーの設定の大半は `setpmac(8)` で行います。このポリシーで使える `sysctl` 調整項目は一つです。

* `security.mac.partition.enabled` は、MACのプロセスパーティションの強制を有効にします。

このポリシーを有効にすると、利用者は自分のプロセスと、同じパーティション内のほかのプロセスだけを見られるようになり、このパーティションの範囲外のユーティリティは使えなくなります。たとえば、`insecure` クラスの利用者は、`top` はもちろん、プロセスを生成する必要のある多くのコマンドを使えません。

次の例は、`insecure` クラスの利用者に設定されるラベルの集合に `top` を追加します。`insecure` クラスの利用者が生成するプロセスは、すべて `partition/13` ラベルのままです。

```shell
# setpmac partition/13 top
```

次のコマンドは、パーティションのラベルとプロセスの一覧を表示します。

```shell
# ps Zax
```

次のコマンドは、別の利用者のプロセスのパーティションラベルと、その利用者が現在実行しているプロセスを表示します。

```shell
# ps -ZU trhodes
```

> **注意**: `mac_seeotheruids(4)` ポリシーを読み込んでいない限り、利用者は `root` のラベルにあるプロセスを見られます。

<a id="mac-mls"></a>
### MAC Multi-Level Securityモジュール

モジュール名: `mac_mls.ko`

カーネル設定行: `options MAC_MLS`

起動オプション: `mac_mls_load="YES"`

`mac_mls(4)` ポリシーは、厳格な情報フローのポリシーを強制して、システム内の主体と客体の間のアクセスを制御します。

MLS環境では、各主体や客体のラベルに、コンパートメントとともに「クリアランス」（clearance）レベルを設定します。このクリアランスレベルは数千を超える数値にもなるため、すべての主体と客体を細かく設定するのは骨の折れる作業です。この管理の手間を減らすため、このポリシーには `mls/low`、`mls/equal`、`mls/high` の3つのラベルが含まれています。それぞれの意味は次のとおりです。

* `mls/low` が付いたものは、クリアランスレベルが低く、より高いレベルの情報にアクセスできません。このラベルは、より高いクリアランスレベルの客体が、低いレベルへ書き込んだり情報を渡したりすることも防ぎます。
* `mls/equal` は、ポリシーの適用から除外すべき客体に設定します。
* `mls/high` は、可能な最高のクリアランスレベルです。このラベルを割り当てた客体は、システム内のほかのすべての客体に対して優位に立ちますが、低いクラスの客体への情報の漏えいは許しません。

MLSが提供するものは次のとおりです。

* 階層的なセキュリティレベルと、階層を持たないカテゴリの集合。
* `no read up, no write down`（上位は読めず、下位へは書けない）という固定の規則。主体は、自分と同じレベルか、それより下の客体は読めますが、上の客体は読めません。同様に、自分と同じレベルか、それより上の客体には書き込めますが、下の客体には書き込めません。
* 機密性、つまりデータの不適切な開示の防止。
* 複数の機密度のデータを同時に扱うシステムで、秘密（secret）と社外秘（confidential）の間で情報を漏らさずに済む設計の基礎。

次の `sysctl` 調整項目が使えます。

* `security.mac.mls.enabled` は、MLSポリシーを有効または無効にします。
* `security.mac.mls.ptys_equal` は、`pty(4)` デバイスを作成するときに、すべて `mls/equal` のラベルにします。
* `security.mac.mls.revocation_enabled` は、客体のラベルがより低いグレードのラベルに変更されたあと、その客体へのアクセスを取り消します。
* `security.mac.mls.max_compartments` は、システムで許されるコンパートメントレベルの最大数を設定します。

MLSラベルの操作には `setfmac(8)` を使います。客体にラベルを割り当てるには、次のようにします。

```shell
# setfmac mls/5 test
```

ファイル `test` のMLSラベルを取得するには、次のようにします。

```shell
# getfmac test
```

別の方法として、MLSポリシーの情報を書いたマスターポリシーファイルを `/etc/` に作り、そのファイルを `setfmac` に読み込ませることもできます。

MLSポリシーモジュールを使うとき、管理者は機微な情報の流れを制御しようとします。既定の `block read up block write down` では、すべてが低い状態に設定されます。すべてにアクセスできる状態から始めて、管理者が少しずつ情報の機密性を高めていきます。

3つの基本ラベルのほかにも、管理者は、必要に応じて利用者やグループをまとめ、それらの間の情報の流れを阻止できます。クリアランスレベルは、`Confidential`（社外秘）、`Secret`（秘）、`Top Secret`（極秘）といった分類のような、わかりやすい言葉で捉えると考えやすいでしょう。プロジェクトのレベルごとに異なるグループを作る管理者もいます。どの分類方法を使うにしても、制限の厳しいポリシーを導入する前に、十分に検討した計画が必要です。

MLSポリシーモジュールの利用が考えられる場面としては、電子商取引のWebサーバー、会社の重要な情報を保管するファイルサーバー、金融機関の環境などがあります。

<a id="mac-biba"></a>
### MAC Bibaモジュール

モジュール名: `mac_biba.ko`

カーネル設定行: `options MAC_BIBA`

起動オプション: `mac_biba_load="YES"`

`mac_biba(4)` モジュールは、MACのBibaポリシーを読み込みます。このポリシーはMLSポリシーに似ていますが、情報フローの規則がやや逆になっています。MLSポリシーが機微な情報の上方向への流れを防ぐのに対し、Bibaは下方向への流れを防ぐためです。

Biba環境では、各主体や客体に「完全性」（integrity）ラベルを設定します。このラベルは、階層的なグレードと、階層を持たない構成要素からなります。グレードが上がるほど、完全性も高くなります。

対応するラベルは `biba/low`、`biba/equal`、`biba/high` で、それぞれの意味は次のとおりです。

* `biba/low` は、客体や主体が持てる最も低い完全性とみなされます。客体や主体にこれを設定すると、`biba/high` の客体や主体への書き込みアクセスは阻止されますが、読み取りアクセスは妨げられません。
* `biba/equal` は、ポリシーの適用から除外するとみなす客体にだけ設定します。
* `biba/high` は、より低いラベルの客体への書き込みを許しますが、その客体の読み取りは許しません。システム全体の完全性に影響する客体に、このラベルを設定することを勧めます。

Bibaが提供するものは次のとおりです。

* 階層的な完全性レベルと、階層を持たない完全性カテゴリの集合。
* MLSとは逆の、`no write up, no read down`（上位へは書けず、下位は読めない）という固定の規則。主体は、自分と同じレベルか、それより下の客体には書き込めますが、上の客体には書き込めません。同様に、自分と同じレベルか、それより上の客体は読めますが、下の客体は読めません。
* データの不適切な変更を防ぐことによる完全性。
* MLSの機密度レベルの代わりに、完全性レベルを使うこと。

Bibaポリシーの操作には、次の調整項目が使えます。

* `security.mac.biba.enabled` は、対象のマシンでBibaポリシーの強制を有効または無効にします。
* `security.mac.biba.ptys_equal` は、`pty(4)` デバイスでBibaポリシーを無効にします。
* `security.mac.biba.revocation_enabled` は、ラベルが主体を支配するものに変更された場合に、その客体へのアクセスを強制的に取り消します。

システムの客体のBibaポリシー設定にアクセスするには、`setfmac` と `getfmac` を使います。

```shell
# setfmac biba/low test
# getfmac test
test: biba/low
```

機密度とは異なる完全性は、信頼できない当事者によって情報が操作されないことを保証するために使います。これには、主体と客体の間で受け渡される情報も含まれます。利用者は、明示的にアクセスを与えられた情報にしか、変更もアクセスもできなくなります。`mac_biba(4)` セキュリティポリシーモジュールを使うと、利用者が見たり実行したりできるファイルとプログラムを管理者が設定でき、しかもそれらのプログラムとファイルが、その利用者に対してシステムに信頼されていることを保証できます。

最初の計画段階で、管理者は、利用者をグレード、レベル、領域に分ける準備をしておく必要があります。このポリシーモジュールを有効にすると、システムは既定でhighのラベルになります。利用者のためにさまざまなグレードとレベルを設定するのは管理者の役目です。クリアランスレベルを使う代わりに、話題（トピック）を使う計画も有効です。たとえば、開発者にだけ、ソースコードリポジトリ、ソースコードのコンパイラ、その他の開発用ユーティリティへの変更アクセスを許します。それ以外の利用者は、テスター、デザイナー、エンドユーザーなど別のカテゴリにまとめ、読み取りアクセスだけを許すといった具合です。

完全性の低い主体は、完全性の高い主体に書き込めず、完全性の高い主体は、完全性の低い客体を一覧することも読むこともできません。ラベルを可能な限り低いグレードに設定すると、主体からアクセスできなくなるおそれがあります。このセキュリティポリシーモジュールに向く環境の例には、制約付きのWebサーバー、開発・テスト用のマシン、ソースコードリポジトリなどがあります。あまり役に立たない実装は、個人用のワークステーション、ルーターとして使うマシン、ネットワークファイアウォールなどです。

<a id="mac-lomac"></a>
### MAC Low-watermarkモジュール

モジュール名: `mac_lomac.ko`

カーネル設定行: `options MAC_LOMAC`

起動オプション: `mac_lomac_load="YES"`

MACのBibaポリシーと違い、`mac_lomac(4)` ポリシーは、完全性の規則を乱さないよう完全性レベルを下げたあとにだけ、より低い完全性の客体へのアクセスを許します。

Low-watermark完全性ポリシーは、ほぼBibaと同じように働きます。違いは、補助グレードのコンパートメントを使って、主体の格下げに対応するために浮動ラベル（floating label）を使う点です。この補助のコンパートメントは `[auxgrade]` の形をとります。補助グレード付きのポリシーを割り当てるときは、`lomac/10[2]` という構文を使います。ここで `2` が補助グレードです。

このポリシーは、システム上のすべての客体に完全性ラベルを付けることを前提としています。主体が完全性の低い客体から読み取りできるようにし、そのあと `[auxgrade]` を使って主体のラベルを格下げすることで、以後の完全性の高い客体への書き込みを防ぎます。Bibaより互換性が高く、初期設定も少なくて済むことがあります。

BibaやMLSのポリシーと同様に、システムの客体にラベルを付けるには `setfmac` と `setpmac` を使います。

```shell
# setfmac /usr/home/trhodes lomac/high[low]
# getfmac /usr/home/trhodes lomac/high[low]
```

> **訳注**: 固定原文のこの例では、`getfmac` にもラベル（`lomac/high[low]`）を渡しています。`getfmac` は、指定したファイルに設定されているラベルを表示するコマンドです（FreeBSD 15.1の [getfmac(8)](https://man.freebsd.org/cgi/man.cgi?query=getfmac&sektion=8) を確認）。実際に試すときは、`getfmac /usr/home/trhodes` のようにファイル名を指定します。

補助グレード `low` は、MAC LOMACポリシーだけが提供する機能です。

<a id="mac-userlocked"></a>
## 利用者の制限

この例では、利用者が50人未満の比較的小さなストレージシステムを想定します。利用者はログインでき、データを保存したり、リソースにアクセスしたりできます。

このシナリオでは、`mac_bsdextended(4)` と `mac_seeotheruids(4)` の各ポリシーモジュールを併用して、システムの客体へのアクセスを阻止しつつ、利用者のプロセスを隠せます。

まず、次の行を `/boot/loader.conf` に追加します。

```
mac_seeotheruids_load="YES"
```

`mac_bsdextended(4)` セキュリティポリシーモジュールは、次の行を `/etc/rc.conf` に追加すると有効になります。

```
ugidfw_enable="YES"
```

`/etc/rc.bsdextended` に保存された既定の規則は、システムの初期化時に読み込まれます。ただし、既定のエントリは変更が必要になるかもしれません。このマシンは利用者へのサービス提供だけを想定しているので、最後の2行以外はすべてコメントアウトしたままにしておいてかまいません。そうすれば、利用者が所有するシステムの客体を既定で読み込ませることになります。

必要な利用者をこのマシンに追加して、再起動します。テストとして、2つのコンソールで別々の利用者としてログインしてみてください。`ps aux` を実行して、ほかの利用者のプロセスが見えるかどうかを確かめます。また、別の利用者のホームディレクトリに対して `ls(1)` を実行すると失敗することも確認します。

スーパーユーザーのアクセスを阻止するよう特定の `sysctl` を変更していない限り、`root` でのテストは試みないでください。

> **注意**: 新しい利用者を追加しても、その利用者の `mac_bsdextended(4)` の規則は、規則集合の一覧には入りません。規則集合をすぐに更新するには、`kldunload(8)` と `kldload(8)` で、セキュリティポリシーモジュールをいったんアンロードして、再び読み込みます。

<a id="mac-implementing"></a>
## MAC jailでのNagios

この節では、MAC環境でネットワーク監視システムのNagiosを実装するのに必要な手順を示します。これは一例であり、本番環境で使う前に、実装したポリシーがネットワークのセキュリティ要件を満たすことを、管理者が自分でテストする必要があります。

この例では、各ファイルシステムに `multilabel` を設定する必要があります。また、MACフレームワークへの統合を試みる前に、`net-mgmt/nagios-plugins`、`net-mgmt/nagios`、`www/apache22` がすべてインストールされ、設定済みで、正しく動作していることを前提とします。

> **訳注**: 固定原文は `www/apache22` を例に挙げていますが、これは古い版のApacheです。現在は `www/apache24` など、新しい版のPortsを使うのが一般的です。この節の手順や設定ファイルのパス（`/usr/local/etc/apache` など）は、原文のまま残しています。実際に導入するときは、使うApacheの版に合わせて読み替えてください。

<a id="chapter-19-heading-22"></a>
### 安全でない利用者クラスの作成

まず、次の利用者クラスを `/etc/login.conf` に追加します。

```
insecure:\
:welcome=/etc/motd:\
:setenv=MAIL=/var/mail/$,BLOCKSIZE=K:\
:path=~/bin:/sbin:/bin:/usr/sbin:/usr/bin:/usr/local/sbin:/usr/local/bin
:manpath=/usr/share/man /usr/local/man:\
:nologin=/usr/sbin/nologin:\
:cputime=1h30m:\
:datasize=8M:\
:vmemoryuse=100M:\
:stacksize=2M:\
:memorylocked=4M:\
:memoryuse=8M:\
:filesize=8M:\
:coredumpsize=8M:\
:openfiles=24:\
:maxproc=32:\
:priority=0:\
:requirehome:\
:passwordtime=91d:\
:umask=022:\
:ignoretime@:\
:label=biba/10(10-10):
```

> **訳注**: 固定原文の上の例では、`:path=` の行の末尾に、ほかの行にある `:\` がありません。設定ファイルに書き写すときは、この行の終わりにも `:\` を付けて、次の行へ続けてください。コードブロックは、原文をそのまま保持しています。

次に、既定の利用者クラスの節に、次の行を追加します。

```
:label=biba/high:
```

編集を保存し、次のコマンドでデータベースを作り直します。

```shell
# cap_mkdb /etc/login.conf
```

<a id="chapter-19-heading-23"></a>
### 利用者の設定

`root` 利用者を、次のコマンドで既定のクラスに設定します。

```shell
# pw usermod root -L default
```

`root` 以外のすべてのユーザーアカウントにも、ログインクラスが必要になります。ログインクラスがないと、利用者は一般的なコマンドの使用を拒否されます。次の `sh` スクリプトで目的を果たせるでしょう。

```shell
# for x in `awk -F: '($3 >= 1001) && ($3 != 65534) { print $1 }' \
	/etc/passwd`; do pw usermod $x -L default; done;
```

続いて、`nagios` と `www` のアカウントを、`insecure` クラスに入れます。

```shell
# pw usermod nagios -L insecure
# pw usermod www -L insecure
```

<a id="chapter-19-heading-24"></a>
### コンテキストファイルの作成

次に、`/etc/policy.contexts` としてコンテキストファイルを作成します。

```
# This is the default BIBA policy for this system.

# System:
/var/run(/.*)?			biba/equal

/dev/(/.*)?			biba/equal

/var				biba/equal
/var/spool(/.*)?		biba/equal

/var/log(/.*)?			biba/equal

/tmp(/.*)?			biba/equal
/var/tmp(/.*)?			biba/equal

/var/spool/mqueue		biba/equal
/var/spool/clientmqueue		biba/equal

# For Nagios:
/usr/local/etc/nagios(/.*)?	biba/10

/var/spool/nagios(/.*)?		biba/10

# For apache
/usr/local/etc/apache(/.*)?	biba/10
```

このポリシーは、情報の流れに制限を設けることでセキュリティを強制します。この構成では、`root` を含む利用者が、Nagiosにアクセスすることは決して許されません。Nagiosに関わる設定ファイルとプロセスは、完全に自己完結した状態、つまり隔離（jail）された状態になります。

このファイルは、各ファイルシステムで `setfsmac` を実行したときに読み込まれます。次の例では、ルートファイルシステムにポリシーを設定します。

```shell
# setfsmac -ef /etc/policy.contexts /
```

次に、`/etc/mac.conf` のメインの節に、次の編集を加えます。

```
default_labels file ?biba
default_labels ifnet ?biba
default_labels process ?biba
default_labels socket ?biba
```

<a id="chapter-19-heading-25"></a>
### ローダーの設定

設定を仕上げるため、次の行を `/boot/loader.conf` に追加します。

```
mac_biba_load="YES"
mac_seeotheruids_load="YES"
security.mac.biba.trust_all_interfaces=1
```

さらに、`/etc/rc.conf` に保存されているネットワークカードの設定に、次の行を追加します。主なネットワーク設定をDHCPで行っている場合は、システムを起動するたびに、これを手作業で設定する必要があるかもしれません。

```
maclabel biba/equal
```

<a id="chapter-19-heading-26"></a>
### 設定のテスト

まず、システムの初期化時や再起動時に、WebサーバーとNagiosが起動しないことを確認します。`root` が、Nagiosの設定ディレクトリ内のどのファイルにもアクセスできないことも確かめてください。`root` が `/var/spool/nagios` の内容を一覧できるなら、どこかがおかしいということです。本来は「permission denied」というエラーが返るはずです。

問題なさそうなら、Nagios、Apache、Sendmailを起動できます。

```shell
# cd /etc/mail && make stop && \
setpmac biba/equal make start && setpmac biba/10\(10-10\) apachectl start && \
setpmac biba/10\(10-10\) /usr/local/etc/rc.d/nagios.sh forcestart
```

すべてが正しく動いているか、よく確認してください。そうでなければ、ログファイルのエラーメッセージを確認します。必要に応じて、`sysctl(8)` で `mac_biba(4)` セキュリティポリシーモジュールを無効にしてから、通常どおりすべての起動をやり直します。

**注意**: `root` 利用者は、セキュリティの強制を変更したり、その設定ファイルを編集したりすることが、依然として可能です。次のコマンドを使うと、新しく起動したシェルについて、セキュリティポリシーをより低いグレードに落とせてしまいます。

```shell
# setpmac biba/10 csh
```

これを防ぐには、`login.conf(5)` を使って利用者を範囲内に固定します。`setpmac(8)` がコンパートメントの範囲外のコマンドを実行しようとすると、エラーが返り、そのコマンドは実行されません。この場合は、rootを `biba/high(high-high)` に設定します。

<a id="mac-troubleshoot"></a>
## MACフレームワークのトラブルシューティング

この節では、よくある設定上の誤りと、その解決方法を説明します。

**ルート（`/`）パーティションで `multilabel` フラグが有効なままにならない場合**

次の手順で、この一時的なエラーが解消することがあります。

1. `/etc/fstab` を編集し、ルートパーティションを読み取り専用の `ro` に設定します。
2. シングルユーザーモードで再起動します。
3. `/` に対して `tunefs -l enable` を実行します。
4. システムを再起動します。
5. `mount -urw /` を実行し、`/etc/fstab` の `ro` を `rw` に戻して、システムをもう一度再起動します。
6. `mount` の出力を再確認し、ルートファイルシステムに `multilabel` が正しく設定されていることを確かめます。

**MACで安全な環境を作ったあと、Xorgが起動しなくなった場合**

MACの `partition` ポリシーが原因か、MACのラベルポリシーのどれかでラベルを誤って付けたことが原因と考えられます。デバッグするには、次を試します。

1. エラーメッセージを確認します。利用者が `insecure` クラスに属しているなら、`partition` ポリシーが原因かもしれません。利用者のクラスを `default` クラスに戻し、`cap_mkdb` でデータベースを作り直してみてください。これで問題が解消しなければ、手順2に進みます。
2. 利用者、Xorg、`/dev` のエントリに対して、ラベルポリシーが正しく設定されているかを再確認します。
3. どちらでも解決しなければ、エラーメッセージと環境の説明を、[FreeBSD-questionsメーリングリスト](https://lists.FreeBSD.org/subscription/freebsd-questions)へ送ってください。

**`_secure_path: unable to stat .login_conf` というエラーが出る場合**

このエラーは、利用者が `root` から別の利用者に切り替えようとしたときに出ることがあります。たいていは、切り替え先の利用者より、切り替え元の利用者のラベル設定が高い場合に発生します。たとえば、`joe` の既定ラベルが `biba/low` で、`root` のラベルが `biba/high` だとすると、`root` は `joe` のホームディレクトリを見られません。`root` が `su` で `joe` になったかどうかにかかわらず、Bibaの完全性モデルは、`root` が低い完全性レベルの客体を見ることを許さないため、このエラーが起こります。

**システムが `root` を認識しなくなった場合**

この場合、`whoami` は `0` を返し、`su` は `who are you?` と返します。

これは、ラベルポリシーが `sysctl(8)` で無効にされたか、ポリシーモジュールがアンロードされた場合に起こりえます。ポリシーが無効になっているなら、ログイン機能データベースを再設定する必要があります。`/etc/login.conf` を再確認し、`label` オプションがすべて削除されていることを確かめたうえで、`cap_mkdb` でデータベースを作り直してください。

また、ポリシーが `master.passwd` へのアクセスを制限している場合にも起こりえます。これは通常、システムが使っている全体のポリシーと矛盾するラベルを付けたまま、管理者がこのファイルを書き換えたことが原因です。こうした場合、システムは利用者情報を読み込んだものの、ファイルが新しいラベルを引き継いだためにアクセスが阻止されます。`sysctl(8)` でポリシーを無効にすれば、すべてが元に戻るはずです。
