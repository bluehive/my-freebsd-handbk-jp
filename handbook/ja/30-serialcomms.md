## 概要

UNIX® では、最初期の UNIX® マシンがユーザーの入出力にシリアル回線を利用していたことから、常にシリアル通信をサポートしてきました。一般的な端末が毎秒 10 文字のシリアルプリンタとキーボードで構成されていた時代から、状況は大きく変わりました。本章では、FreeBSD でシリアル通信を利用するいくつかの方法を説明します。

本章を読むと、次の内容を学べます。

* FreeBSD システムに端末を接続する方法
* モデムを使ってリモートホストへダイヤルアウトする方法
* モデム経由でリモートユーザーが FreeBSD システムへログインできるようにする方法
* シリアルコンソールから FreeBSD システムを起動する方法

本章を読む前に、次の準備を整えておいてください。

* [カスタムカーネルを設定してインストールする方法](09-kernelconfig.md#kernelconfig)を理解しておくこと
* [FreeBSD のパーミッションとプロセス](03-basics.md#basics)を理解しておくこと
* FreeBSD で使用するシリアルハードウェアの技術マニュアルを手元に用意しておくこと

## シリアル通信の用語とハードウェア

シリアル通信では、次の用語がよく使われます。

**bps**
: Bits per Second（ビット毎秒）の略で、データが転送される速度を表します。

**DTE**
: Data Terminal Equipment（データ端末装置）の略で、シリアル通信における 2 つの端点のうち一方を指します。たとえばコンピュータがこれに該当します。

**DCE**
: Data Communications Equipment（データ回線終端装置）の略で、シリアル通信におけるもう一方の端点を指します。通常はモデムやシリアル端末です。

**RS-232**
: ハードウェアのシリアル通信を定義した元の規格です。その後、TIA-232 へと改称されました。

この節では通信のデータ転送速度を表す際に *ボー（baud）* という用語は使いません。ボーは単位時間あたりの電気的な状態遷移の回数を指すものであり、データ転送速度には bps を使うのが正確です。

FreeBSD システムにシリアル端末を接続するには、コンピュータ側のシリアルポートと、シリアルデバイスを接続するための適切なケーブルが必要です。シリアルハードウェアやケーブル配線にすでに詳しい場合は、この節を読み飛ばしても構いません。

<a id="term-cables-null"></a>
### シリアルケーブルとポート

シリアルケーブルにはいくつかの種類がありますが、最も一般的なのはヌルモデムケーブルと標準 RS-232 ケーブルの 2 種類です。必要なケーブルの種類については、ハードウェアの説明書を確認してください。

これら 2 種類のケーブルは、コネクタへの配線のつなぎ方が異なります。各導線は 1 つの信号に対応しており、定義されている信号は [RS-232C 信号名](#serialcomms-signal-names) にまとめています。標準シリアルケーブルは、すべての RS-232C 信号をストレートに通します。たとえば、ケーブルの一端の「Transmitted Data（送信データ）」ピンは、もう一端の「Transmitted Data」ピンにつながります。この種類のケーブルはモデムを FreeBSD システムに接続するときに使われ、一部の端末でも使用されます。

一方、ヌルモデムケーブルは、一端のコネクタの「Transmitted Data」ピンともう一端の「Received Data（受信データ）」ピンを交差させて接続します。コネクタは DB-25 または DB-9 のいずれかです。

ヌルモデムケーブルは、[DB-25 対 DB-25 ヌルモデムケーブル](#nullmodem-db25)、[DB-9 対 DB-9 ヌルモデムケーブル](#nullmodem-db9)、および [DB-9 対 DB-25 ヌルモデムケーブル](#nullmodem-db9-25) にまとめたピン結線を使って自作することもできます。規格上はピン 1 同士をストレートにつなぐ「Protective Ground（保護接地）」線が規定されていますが、実際には省略されることがよくあります。端末によってはピン 2・3・7 のみで動作するものもあれば、別の結線を必要とするものもあります。判断に迷う場合は、ハードウェアの説明書を参照してください。

シリアルポートは、FreeBSD ホストコンピュータと端末との間でデータをやり取りするためのデバイスです。シリアルポートにはいくつかの種類があるため、ケーブルを購入したり自作したりする前に、端末側と FreeBSD システム側の双方のポート形状に適合することを確認してください。

ほとんどの端末には DB-25 ポートが搭載されています。パーソナルコンピュータでは DB-25 または DB-9 ポートが使われます。マルチポートシリアルカードでは RJ-12 や RJ-45 ポートを備えている場合があります。ポートの種類については、ハードウェアに付属の説明書で仕様を確認するか、目視で確認してください。

FreeBSD では、各シリアルポートは `/dev` 配下のエントリを通じてアクセスします。エントリには次の 2 種類があります。

* 着信（call-in）ポートは `/dev/ttyuN` という名前になります（*N* は 0 から始まるポート番号）。端末が 1 番目のシリアルポート（`COM1`）に接続されている場合は `/dev/ttyu0` を、2 番目のシリアルポート（`COM2`）に接続されている場合は `/dev/ttyu1` を指定します（以降同様）。通常、着信ポートは端末に使用されます。着信ポートが正常に動作するには、シリアル回線で「Data Carrier Detect（DCD）」信号がアサートされている必要があります。
* 発信（call-out）ポートは、FreeBSD 8.X 以降では `/dev/cuauN`、FreeBSD 7.X 以前では `/dev/cuadN` という名前になります。発信ポートは通常は端末には使わず、モデムに使用します。ただし、シリアルケーブルや端末が「Data Carrier Detect」信号に対応していない場合には、発信ポートを使用することもできます。

FreeBSD には、初期化デバイス（`/dev/ttyuN.init` および `/dev/cuauN.init`、あるいは `/dev/cuadN.init`）とロックデバイス（`/dev/ttyuN.lock` および `/dev/cuauN.lock`、あるいは `/dev/cuadN.lock`）も用意されています。初期化デバイスは、ポートが開かれるたびに通信ポートのパラメータを初期化するために使用します（たとえば `RTS/CTS` 信号によるフロー制御を行うモデム向けに `crtscts` を設定するなど）。ロックデバイスは、ユーザーやプログラムが特定のパラメータを変更できないよう、ポートのフラグを固定するために使用します。端末設定、ロックデバイスと初期化デバイス、および端末オプションの設定については、それぞれ `termios(4)`、`uart(4)`、`stty(1)` の man ページを参照してください。

<a id="serial-hw-config"></a>
### シリアルポートの設定

デフォルトでは、FreeBSD は一般に `COM1`、`COM2`、`COM3`、`COM4` と呼ばれる 4 つのシリアルポートをサポートしています。また、BocaBoard 1008 や 2016 といったダム型のマルチポートシリアルインターフェースカードや、Digiboard 製のような高機能なマルチポートカードもサポートしています。ただし、デフォルトカーネルが検出するのは標準の `COM` ポートのみです。

システムがシリアルポートを認識しているか確認するには、`uart` で始まるシステム起動メッセージを調べます。

```shell
# grep uart /var/run/dmesg.boot
```

必要なシリアルポートがすべて認識されていない場合は、`/boot/device.hints` にエントリを追加できます。このファイルには、`COM1` 用の `hint.uart.0.*` エントリと `COM2` 用の `hint.uart.1.*` エントリがすでに含まれています。`COM3` のポートエントリを追加する場合はアドレスに `0x3E8`、`COM4` の場合は `0x2E8` を使用します。一般的な IRQ 番号は `COM3` が `5`、`COM4` が `9` です。

ポートで使われているデフォルトの端末 I/O 設定を確認するには、そのデバイス名を指定します。次の例では、`COM2` の着信ポートの設定を確認しています。

```shell
# stty -a -f /dev/ttyu1
```

シリアルデバイスのシステム全体の初期化は `/etc/rc.d/serial` によって制御されており、このファイルがシリアルデバイスのデフォルト設定に影響します。デバイスの設定を変更するには `stty` を使用します。デフォルトでは、変更した設定はそのデバイスが閉じられるまで有効で、次に開き直すとデフォルト設定に戻ります。デフォルト設定を恒久的に変更するには、初期化デバイスを開いて設定を調整します。たとえば、`ttyu5` で `CLOCAL` モード、8 ビット通信、および `XON/XOFF` フロー制御を有効にするには、次のように入力します。

```shell
# stty -f /dev/ttyu5.init clocal cs8 ixon ixoff
```

アプリケーションによって特定の設定が変更されないようにするには、ロックデバイスに対して設定を行います。たとえば、`ttyu5` の通信速度を 57600 bps に固定するには、次のように入力します。

```shell
# stty -f /dev/ttyu5.lock 57600
```

これにより、今後 `ttyu5` を開いてポートの速度を変更しようとするアプリケーションがあっても、57600 bps に固定されたままになります。

<a id="term"></a>
## 端末

端末（ターミナル）は、コンピュータ本体のコンソール前におらず、ネットワーク接続もない状況で FreeBSD システムへアクセスするための、手軽で低コストな手段を提供します。この節では、FreeBSD で端末を使用する方法を説明します。

初期の UNIX® システムにはコンソールがなく、ユーザーはコンピュータのシリアルポートに接続された端末からログインし、プログラムを実行していました。

シリアルポート上でログインセッションを確立する機能は、FreeBSD をはじめ今日のほぼすべての UNIX® 系オペレーティングシステムに今も残っています。未使用のシリアルポートに端末を接続すれば、ユーザーはログインして、通常コンソールや `xterm` ウィンドウで実行できるテキストプログラムをすべて実行できます。

FreeBSD システムには多数の端末を接続できます。古い予備のコンピュータを端末として、より高性能な FreeBSD コンピュータへケーブル接続することも可能です。これにより、通常ならシングルユーザー機にとどまるコンピュータを、強力なマルチユーザーシステムとして活用できます。

FreeBSD は次の 3 種類の端末をサポートしています。

**ダム端末（Dumb terminals）**
: ダム端末は、シリアル回線経由でコンピュータに接続する専用ハードウェアです。テキストの表示・送信・受信に足るだけの処理能力しか持たないため「ダム（dumb）」と呼ばれます。この機器自体ではプログラムを実行できず、必要なプログラムを実行するコンピュータへ接続して使います。

  ダム端末には多くのメーカーによる何百種類もの製品があり、ほぼどの機種でも FreeBSD で動作します。上位機種の中にはグラフィックスを表示できるものもありますが、そうした高度な機能を利用できるのは一部のソフトウェアパッケージに限られます。

  ダム端末は、グラフィカルなアプリケーションへのアクセスを必要としない作業環境で広く利用されています。

**端末として動作させるコンピュータ**
: ダム端末に求められるのはテキストの表示・送信・受信能力だけなので、余っているコンピュータであればどれでもダム端末として利用できます。必要なのは適切なケーブルと、そのコンピュータ上で動作する *端末エミュレーション* ソフトウェアだけです。

  この構成は実用面でも便利です。たとえば、あるユーザーが FreeBSD システムのコンソールで作業している最中に、別のユーザーが端末として接続した非力なパーソナルコンピュータから同時にテキストベースの作業を行うことができます。

  FreeBSD のベースシステムには、シリアル接続経由で作業するためのユーティリティが少なくとも 2 つ含まれています。`cu(1)` と `tip(1)` です。

  たとえば、FreeBSD が動作するクライアントシステムから別のシステムのシリアル接続へつなぐには、次のようにします。

```shell
# cu -l /dev/cuauN
```

  ポート番号は 0 から始まります。つまり、`COM1` は `/dev/cuau0` です。

  このほかにも、`comms/minicom` などの追加プログラムが Ports Collection から利用できます。

**X 端末**
: X 端末は最も高機能な種類の端末です。シリアルポートではなく、通常は Ethernet のようなネットワークに接続します。また、テキスト専用アプリケーションに限定されず、あらゆる Xorg アプリケーションを表示できます。

  本章では X 端末のセットアップ、設定、および利用方法は扱いません。

<a id="term-config"></a>
### 端末の設定

この節では、シリアル端末上でログインセッションを有効にするための FreeBSD システムの設定手順を説明します。端末が接続されているシリアルポートをシステムがすでに認識しており、適切なケーブルで端末が接続されていることを前提とします。

FreeBSD では、`init` が `/etc/ttys` を読み込み、利用可能な端末に対して `getty` プロセスを起動します。`getty` プロセスはログイン名を読み取り、`login` プログラムを起動する役割を担います。FreeBSD システム上でログインを許可するポートは `/etc/ttys` に列挙されています。たとえば、1 番目の仮想コンソールである `ttyv0` はこのファイルにエントリがあり、コンソールからのログインを許可しています。このファイルには他の仮想コンソール、シリアルポート、疑似端末（pseudo-tty）のエントリも含まれます。直結（ハードワイヤード）端末の場合、シリアルポートの `/dev` エントリから `/dev` の部分を除いて記述します。たとえば `/dev/ttyv0` は `ttyv0` と記述します。

デフォルトの `/etc/ttys` では、最初の 4 つのシリアルポート（`ttyu0` から `ttyu3`）のサポートが次のように設定されています。

```
ttyu0   "/usr/libexec/getty std.115200"   dialup  off secure
ttyu1   "/usr/libexec/getty std.115200"   dialup  off secure
ttyu2   "/usr/libexec/getty std.115200"   dialup  off secure
ttyu3   "/usr/libexec/getty std.115200"   dialup  off secure
```

これらのポートのいずれかに端末を接続する場合は、デフォルトのエントリを編集して必要な通信速度と端末タイプを設定し、デバイスを `on` に切り替え、必要に応じてポートの `secure` 設定を変更します。これら以外のポートに端末を接続している場合は、そのポート用のエントリを追加します。

[端末エントリの設定](#ex-etc-ttys) では、`/etc/ttys` に 2 台の端末を設定しています。1 つ目のエントリは `COM2` に接続された Wyse-50 の設定です。2 つ目のエントリは、VT-100 端末をエミュレートする Procomm 端末ソフトウェアを実行している古いコンピュータの設定で、マルチポートシリアルカードの 6 番目のシリアルポートに接続されています。

<a id="ex-etc-ttys"></a>
**例: 端末エントリの設定**

```
ttyu1  "/usr/libexec/getty std.38400"  wy50   on insecure
ttyu5   "/usr/libexec/getty std.19200"  vt100  on insecure
```

第 1 フィールドにはシリアル端末のデバイス名を指定します。

第 2 フィールドは、`getty` に対して回線の初期化とオープン、回線速度の設定、ユーザー名の入力プロンプト表示、そして `login` プログラムの実行を指示するものです。省略可能な *getty タイプ* で、bps 速度やパリティといった端末回線の特性を設定します。利用可能な getty タイプは `/etc/gettytab` に一覧されています。ほとんどすべての場合、直結端末では `std` で始まる getty タイプがそのまま動作します（これらのエントリはパリティを無視します）。110 から 115200 までの各 bps 速度に対応する `std` エントリが用意されています。詳細は `gettytab(5)` の man ページを参照してください。getty タイプを設定する際は、端末側で使っている通信設定と一致させてください。この例では、Wyse-50 はパリティなし・38400 bps で接続し、古いコンピュータはパリティなし・19200 bps で接続します。

第 3 フィールドは端末の種類です。ダイヤルアップポートでは、ユーザーが事実上あらゆる種類の端末やソフトウェアで接続してくるため、通常は `unknown` または `dialup` を使用します。一方、直結端末では端末の種類が変わらないため、`/etc/termcap` にある実際の端末タイプを指定できます。この例では、Wyse-50 には実機の端末タイプを指定し、Procomm を実行しているコンピュータにはエミュレート対象の VT-100 を指定しています。

第 4 フィールドはそのポートを有効にするかどうかを指定します。このポートでのログインを有効にするには、`on` を設定する必要があります。

最後のフィールドは、そのポートが安全（secure）かどうかを指定します。ポートを `secure` に設定すると、そのポートから `root` が直接ログインできるほど信頼されていることを意味します。`insecure` なポートでは `root` の直接ログインは許可されません。`insecure` なポートでは、[スーパーユーザーアカウント](03-basics.md#users-superuser)で説明されているように、ユーザーはいったん非特権アカウントでログインしたあと、`su` などの仕組みを使ってスーパーユーザー権限を取得する必要があります。セキュリティ上の理由から、この設定は `insecure` に変更することを推奨します。

`/etc/ttys` を変更したあとは、`init` プロセスへ SIGHUP（ハングアップ）シグナルを送り、設定ファイルを強制的に再読み込みさせます。

```shell
# kill -HUP 1
```

`init` は常にシステムで最初に起動されるプロセスであるため、そのプロセス ID は必ず `1` になります。

すべての設定が正しく行われ、ケーブルが接続されていて、端末の電源が入っていれば、各端末に対して `getty` プロセスが起動し、それぞれの端末にログインプロンプトが表示されるはずです。

<a id="term-debug"></a>
### 接続のトラブルシューティング

どれほど細心に手順を進めても、端末のセットアップ中に問題が生じることはあります。よくある症状と対処法の例を次に示します。

ログインプロンプトが表示されない場合は、端末の電源コードが差し込まれ電源が入っていることを確認してください。パーソナルコンピュータを端末として使っている場合は、正しいシリアルポートに対して端末エミュレーションソフトウェアが起動していることを確認してください。

ケーブルが端末側と FreeBSD コンピュータ側の双方にしっかり差し込まれていること、および適切な種類のケーブルであることを確認してください。

端末側と FreeBSD 側で bps 速度とパリティの設定が一致していることを確認してください。ビデオディスプレイ端末の場合は、コントラストや輝度の調整が十分上がっていることを確認してください。印字端末（プリンティングターミナル）の場合は、用紙とインクが十分にあることを確認してください。

`ps` を使って、`getty` プロセスが起動してその端末を担当しているか確認します。たとえば次の出力では、2 番目のシリアルポートである `ttyu1` 上で `getty` が動作し、`/etc/gettytab` の `std.38400` エントリを使用していることがわかります。

```shell
# ps -axww|grep ttyu
22189  d1  Is+    0:00.03 /usr/libexec/getty std.38400 ttyu1
```

`getty` プロセスが動作していない場合は、`/etc/ttys` でそのポートが有効になっているか確認してください。`/etc/ttys` を変更したあとは、忘れずに `kill -HUP 1` を実行してください。

`getty` プロセスは動作しているのにログインプロンプトが表示されない場合、またはプロンプトは表示されるもののキー入力を受け付けない場合は、端末またはケーブルがハードウェアハンドシェイクに対応していない可能性があります。`/etc/ttys` のエントリを `std.38400` から `3wire.38400` へ変更し、変更後に `kill -HUP 1` を実行してみてください。`3wire` エントリは `std` と似ていますが、ハードウェアハンドシェイクを無視します。`3wire` を使用する場合は、バッファオーバーフローを防ぐために bps 速度を下げるか、ソフトウェアフロー制御を有効にする必要が生じることもあります。

ログインプロンプトの代わりに文字化けが表示される場合は、端末と FreeBSD の間で bps 速度とパリティ設定が一致しているか確認してください。`getty` プロセスを確認し、正しい *getty* タイプが使われているか確かめてください。異なっている場合は、`/etc/ttys` を編集して `kill -HUP 1` を実行します。

文字が二重に表示され、入力したパスワードまで画面に表示されてしまう場合は、端末または端末エミュレーションソフトウェアの設定を「半二重（half duplex）」または「ローカルエコー（local echo）」から「全二重（full duplex）」へ切り替えてください。

<a id="dialup"></a>
## ダイヤルインサービス

ダイヤルインサービス用に FreeBSD システムを設定する手順は、端末デバイスの代わりにモデムを使う点を除けば、端末の設定とよく似ています。FreeBSD は外付けモデムと内蔵モデムの両方をサポートしています。

外付けモデムは、不揮発性 RAM にパラメータを保存して設定できることが多く、また重要な RS-232 信号の状態を示すランプ（インジケータ）を備えていてモデムが正常に動作しているか一目でわかるため、扱いやすいのが利点です。

内蔵モデムは通常、不揮発性 RAM を持たないため、設定が DIP スイッチに限られることがあります。また、信号インジケータランプが付いていたとしても、本体のカバーを閉じた状態では確認しにくくなります。

外付けモデムを使用する場合は、適切なケーブルが必要です。標準の RS-232C シリアルケーブルで問題ありません。

FreeBSD では、2400 bps を超える速度でのフロー制御に RTS と CTS 信号、着信応答や回線切断の検出に CD 信号、セッション終了後にモデムをリセットするために DTR 信号が必要になります。ケーブルによっては必要な信号線がすべて結線されていないものもあるため、回線が切断されてもログインセッションが終了しない場合はケーブルに問題がある可能性があります。これらの信号の詳細については、[シリアルケーブルとポート](#term-cables-null)を参照してください。

他の UNIX® 系オペレーティングシステムと同様に、FreeBSD は着信への応答や回線切断の検出、通話後のモデムの切断とリセットにハードウェア信号を使用します。FreeBSD はモデムへコマンドを送信したり、モデムからのステータス報告を監視したりする方式を避けています。

FreeBSD は、NS8250、NS16450、NS16550、および NS16550A ベースの RS-232C（CCITT V.24）通信インターフェースをサポートしています。8250 と 16450 デバイスは 1 文字分のバッファしか持ちません。16550 デバイスは 16 文字分のバッファを備えており、より高いシステム性能が得られます。ただし無印の 16550 デバイスには 16 文字バッファの使用を妨げるバグがあるため、可能であれば 16550A デバイスを使用してください。1 文字バッファのデバイスは 16 文字バッファのデバイスよりもオペレーティングシステム側の処理負荷が大きくなるため、16550A ベースのシリアルインターフェースカードが望ましいです。稼働中のシリアルポートが多いシステムや高負荷なシステムでは、エラー率の低い通信のために 16550A ベースのカードの方が適しています。

この節の残りでは、着信接続を受け付けるためのモデムの設定方法、モデムとの通信方法、およびいくつかのトラブルシューティングのヒントを説明します。

<a id="dialup-ttys"></a>
### モデムの設定

端末の場合と同様に、`init` はダイヤルイン接続用に設定された各シリアルポートに対して `getty` プロセスを起動します。ユーザーがモデムの回線にダイヤルしてモデム同士が接続すると、モデムから「Carrier Detect（キャリア検出）」信号が通知されます。カーネルはキャリアの検出を検知すると、`getty` に対してポートを開き、指定された初期回線速度で `login:` プロンプトを表示するよう指示します。一般的な構成では、モデムの接続速度が設定速度と異なることなどが原因で文字化けを受信した場合、`getty` は正常な文字を受信できるまで回線速度を切り替えながら調整を試みます。ユーザーがログイン名を入力すると、`getty` は `login` を実行し、`login` がパスワードの入力を求めてユーザーのシェルを起動することでログイン処理が完了します。

ダイヤルアップモデムの設定には 2 つの考え方があります。1 つ目の方法は、リモートユーザーがどの速度でダイヤルインしてきても、ダイヤルイン用の RS-232 インターフェースを固定速度で動作させるようにモデムとシステムを設定するやり方です。この構成の利点は、リモートユーザーに常に即座にシステムのログインプロンプトが表示されることです。欠点は、システム側がユーザーの実際のデータ転送速度を把握できないため、Emacs のようなフルスクリーンプログラムが低速回線向けに表示更新方法を調整できない点です。

2 つ目の方法は、リモートユーザーの接続速度に合わせて RS-232 インターフェースの速度を可変にするやり方です。`getty` は特定のモデムが出す接続速度の通知を解釈しないため、まず初期速度で `login:` メッセージを送信し、返ってくる文字を監視します。ユーザー側で文字化けが表示された場合は、読み取れるプロンプトが出るまで `Enter` キーを押し続けます。データ転送速度が一致していなければ、`getty` はユーザーの入力をすべてゴミデータとみなし、次の速度を試して再度 `login:` プロンプトを表示します。通常、この手順は 1〜2 回キーを押すだけで正常なプロンプトが表示されます。このログイン手順は固定速度方式ほどすっきりした見た目にはなりませんが、低速接続のユーザーにとってはフルスクリーンプログラムの対話的な応答性が向上します。

モデムのデータ通信速度を特定の速度に固定する場合は、`/etc/gettytab` の変更は不要なはずです。一方、速度追従（matching-speed）構成にする場合は、モデムで使用する速度を定義するためのエントリを追加する必要があるかもしれません。

次の例では、最大インターフェース速度が 19.2 Kbps の 14.4 Kbps モデムを、8 ビット・パリティなし接続で設定しています。V.32bis 接続の通信速度を 19.2 Kbps から開始し、順に 9600 bps、2400 bps、1200 bps、300 bps と巡回して再び 19.2 Kbps に戻るよう `getty` を設定します。通信速度の巡回は `nx=`（next table）ケイパビリティで実装しています。各行では `tc=`（table continuation）エントリを使って、該当するデータ速度の残りの設定を引き継いでいます。

```
#
# Additions for a V.32bis Modem
#
um|V300|High Speed Modem at 300,8-bit:\
        :nx=V19200:tc=std.300:
un|V1200|High Speed Modem at 1200,8-bit:\
        :nx=V300:tc=std.1200:
uo|V2400|High Speed Modem at 2400,8-bit:\
        :nx=V1200:tc=std.2400:
up|V9600|High Speed Modem at 9600,8-bit:\
        :nx=V2400:tc=std.9600:
uq|V19200|High Speed Modem at 19200,8-bit:\
        :nx=V9600:tc=std.19200:
```

28.8 Kbps モデムを使う場合や、14.4 Kbps モデムのデータ圧縮機能を活用する場合は、次の例のように、より高い通信速度を設定します。

```
#
# Additions for a V.32bis or V.34 Modem
# Starting at 57.6 Kbps
#
vm|VH300|Very High Speed Modem at 300,8-bit:\
        :nx=VH57600:tc=std.300:
vn|VH1200|Very High Speed Modem at 1200,8-bit:\
        :nx=VH300:tc=std.1200:
vo|VH2400|Very High Speed Modem at 2400,8-bit:\
        :nx=VH1200:tc=std.2400:
vp|VH9600|Very High Speed Modem at 9600,8-bit:\
        :nx=VH2400:tc=std.9600:
vq|VH57600|Very High Speed Modem at 57600,8-bit:\
        :nx=VH9600:tc=std.57600:
```

CPU が遅いシステムや、16550A ベースのシリアルポートを搭載していない高負荷なシステムでは、この設定にすると 57.6 Kbps で `uart` の「silo」エラーが発生することがあります。

`/etc/ttys` の設定は [端末エントリの設定](#ex-etc-ttys) と似ていますが、`getty` に渡す引数が異なり、端末タイプには `dialup` を使用します。*xxx* の部分は、そのデバイス上で `init` が実行するプロセスに置き換えます。

```
ttyu0   "/usr/libexec/getty xxx"   dialup on
```

端末タイプ `dialup` は変更することもできます。たとえば、デフォルトの端末タイプを `vt102` に設定すれば、ユーザーはリモートシステム側で VT102 エミュレーションを利用できます。

固定速度構成では、`/etc/gettytab` に記載されている有効なタイプを使って速度を指定します。次の例は、ポート速度を 19.2 Kbps に固定したモデムの設定です。

```
ttyu0   "/usr/libexec/getty std.19200"   dialup on
```

速度追従構成では、`/etc/gettytab` 内の適切な開始用「auto-baud」エントリを参照する必要があります。19.2 Kbps から開始する速度追従モデムの例を続けると、次のエントリを使用します。

```
ttyu0   "/usr/libexec/getty V19200"   dialup on
```

`/etc/ttys` を編集したあとは、モデムの設定と接続が正しく完了するのを待ってから、`init` にシグナルを送ります。

```shell
# kill -HUP 1
```

V.32、V.32bis、V.34 モデムのような高速モデムでは、ハードウェア（`RTS/CTS`）フロー制御を使用します。モデムポートにハードウェアフロー制御フラグを設定するには `stty` を使います。次の例では、`COM2` のダイヤルイン用およびダイヤルアウト用の初期化デバイスに `crtscts` フラグを設定しています。

```shell
# stty -f /dev/ttyu1.init crtscts
# stty -f /dev/cuau1.init crtscts
```

<a id="chapter-30-heading-11"></a>
### トラブルシューティング

この節では、ダイヤルアップモデムが FreeBSD システムに接続できない場合のトラブルシューティングのヒントをいくつか紹介します。

モデムを FreeBSD システムに接続し、システムを起動します。モデムに状態表示ランプがある場合は、システムのコンソールに `login:` プロンプトが表示されたタイミングでモデムの DTR インジケータが点灯するか確認してください。点灯していれば、FreeBSD が該当する通信ポートで `getty` プロセスを起動し、モデムが着信を受け付けるのを待っている状態であることを意味します。

DTR インジケータが点灯しない場合は、コンソールから FreeBSD システムにログインし、`ps ax` を実行して、正しいポートで `getty` プロセスが動作しているか確認します。

```shell
  114 ??  I      0:00.10 /usr/libexec/getty V19200 ttyu0
```

モデムがまだ着信に応答していないにもかかわらず、2 列目が `??` ではなく `d0` になっている場合、`getty` がすでに通信ポートのオープンを完了していることを意味します。本来、モデムからキャリア検出信号がアサートされるまで `getty` は通信ポートを開けないはずなので、ケーブル配線に問題があるか、モデムの設定が誤っている可能性があります。

ポートのオープンを待機している `getty` プロセスが存在しない場合は、`/etc/ttys` の該当ポートのエントリが正しいか再確認してください。また、`/var/log/messages` を確認し、`init` や `getty` からのログメッセージが出ていないかも調べてください。

次に、システムへダイヤルインしてみます。リモートシステム側の設定は、8 ビット・パリティなし・ストップビット 1 に必ず合わせてください。すぐにプロンプトが表示されない場合や文字化けが出る場合は、約 1 秒おきに `Enter` キーを押してみてください。それでも `login:` プロンプトが出ない場合は、`BREAK` の送信を試してください。高速モデムを使用している場合は、発信側モデムのインターフェース速度を固定したうえで再度ダイヤルしてみてください。

それでも `login:` プロンプトが表示されない場合は、`/etc/gettytab` をもう一度見直し、次の点を確認してください。

* `/etc/ttys` のエントリで指定した最初のケイパビリティ名が、`/etc/gettytab` 内のケイパビリティ名と一致していること
* 各 `nx=` エントリが、別の `gettytab` ケイパビリティ名と一致していること
* 各 `tc=` エントリが、別の `gettytab` ケイパビリティ名と一致していること

FreeBSD システム側のモデムが着信に応答しない場合は、DTR がアサートされているときに着信応答するようモデムが設定されているか確認してください。モデムの設定が正しいと思われる場合は、モデムのインジケータランプを見て DTR 線がアサートされているか確かめてください。

それでも動作しない場合は、使用しているモデムと発生している問題を記載して [freebsd-questions メーリングリスト](https://lists.freebsd.org/subscription/freebsd-questions) へメールを送ってみてください。

<a id="dialout"></a>
## ダイヤルアウトサービス

以下では、ホストからモデム経由で別のコンピュータへ接続するためのヒントを紹介します。リモートホストとの端末セッションを確立する用途に適しています。

この種の接続は、PPP の使用に問題がある場合にインターネット上のファイルを取得するのにも役立ちます。PPP が動作しないときは、端末セッションを使って必要なファイルを FTP で取得し、その後 zmodem を使って手元のマシンへ転送します。

<a id="hayes-unsupported"></a>
### 標準的な Hayes モデムを使う

`tip` には汎用的な Hayes ダイヤラが組み込まれています。`/etc/remote` で `at=hayes` を指定してください。

この Hayes ドライバは、新しいモデムが持つ高度な機能によるメッセージ（`BUSY`、`NO DIALTONE`、`CONNECT 115200` など）を認識できるほど賢くありません。`tip` を使う際は、`ATX0&W` でこれらのメッセージを無効にしてください。

`tip` のダイヤルタイムアウトは 60 秒です。モデム側にはそれより短い値を設定しないと、`tip` は通信障害が発生したと判断してしまいます。`ATS7=45&W` を試してください。

<a id="direct-at"></a>
### `AT` コマンドを使う

`/etc/remote` に「direct（直接接続）」エントリを作成します。たとえば、モデムが 1 番目のシリアルポートである `/dev/cuau0` に接続されている場合は、次の行を記述します。

```
cuau0:dv=/dev/cuau0:br#19200:pa=none
```

`br` ケイパビリティには、そのモデムがサポートする最大の bps 速度を指定してください。次に、`tip cuau0` と入力してモデムへ接続します。

あるいは、`root` 権限で `cu` を使い、次のコマンドを実行することもできます。

```shell
# cu -lline -sspeed
```

*line* には `/dev/cuau0` などのシリアルポート、*speed* には `57600` などの速度を指定します。AT コマンドの入力が終わったら、`~.` と入力して終了します。

<a id="gt-failure"></a>
### `@` 記号が機能しない

電話番号ケイパビリティ内の `@` 記号は、`/etc/phones` から電話番号を検索するよう `tip` に指示します。しかし、`@` 記号は `/etc/remote` のようなケイパビリティファイルにおける特殊文字でもあるため、バックスラッシュでエスケープする必要があります。

```
pn=\@
```

<a id="dial-command-line"></a>
### コマンドラインからダイヤルする

`/etc/remote` に「汎用（generic）」エントリを記述します。例を示します。

```
tip115200|Dial any phone number at 115200 bps:\
        :dv=/dev/cuau0:br#115200:at=hayes:pa=none:du:
tip57600|Dial any phone number at 57600 bps:\
        :dv=/dev/cuau0:br#57600:at=hayes:pa=none:du:
```

これで、次のコマンドが動作するはずです。

```shell
# tip -115200 5551234
```

`tip` より `cu` を好む場合は、汎用的な `cu` エントリを使用できます。

```
cu115200|Use cu to dial any number at 115200bps:\
        :dv=/dev/cuau1:br#57600:at=hayes:pa=none:du:
```

> **訳注**: 原文の例ではエントリ名が `cu115200`（115200bps）となっていますが、設定値は `br#57600` のまま記載されています。原文どおり保持しています。

そのうえで、次のように入力します。

```shell
# cu 5551234 -s 115200
```

<a id="set-bps"></a>
### bps 速度を設定する

`tip1200` または `cu1200` のエントリを作成し、`br` ケイパビリティには実際に適切な任意の bps 速度を指定してください。`tip` は 1200 bps を適切なデフォルト値とみなしているため `tip1200` エントリを探しますが、実際に 1200 bps を使う必要はありません。

<a id="terminal-server"></a>
### ターミナルサーバー経由で複数のホストへアクセスする

接続されるのを待ってから毎回 `CONNECT` *host* と入力する代わりに、`tip` の `cm` ケイパビリティを使用します。たとえば、`/etc/remote` に次のエントリを記述しておくと、`tip pain` や `tip muffin` と入力するだけでホスト `pain` や `muffin` に接続でき、`tip deep13` と入力するとターミナルサーバーへ接続できます。

```
pain|pain.deep13.com|Forrester's machine:\
        :cm=CONNECT pain\n:tc=deep13:
muffin|muffin.deep13.com|Frank's machine:\
        :cm=CONNECT muffin\n:tc=deep13:
deep13:Gizmonics Institute terminal server:\
        :dv=/dev/cuau2:br#38400:at=hayes:du:pa=none:pn=5551234:
```

<a id="tip-multiline"></a>
### `tip` で複数の回線を使う

大学などにモデム回線が複数あり、数千人の学生がそれらを利用しようとするような場面では、複数回線の扱いがよく問題になります。

`/etc/remote` にエントリを作成し、`pn` ケイパビリティに `@` を指定します。

```
big-university:\
        :pn=\@:tc=dialout
dialout:\
        :dv=/dev/cuau3:br#9600:at=courier:du:pa=none:
```

次に、`/etc/phones` に電話番号を列挙します。

```
big-university 5551111
big-university 5551112
big-university 5551113
big-university 5551114
```

`tip` は記載された順に各番号への接続を試み、すべて失敗すると終了します。接続できるまで繰り返し試行したい場合は、`while` ループの中で `tip` を実行してください。

<a id="multi-controlp"></a>
### フォース文字（Force Character）を使う

`Ctrl+P` はデフォルトの「フォース（force）」文字であり、次の 1 文字をそのままリテラルデータとして扱うよう `tip` に伝えるために使われます。フォース文字は、「変数を設定する」という意味の `~s` エスケープを使って別の任意の文字へ変更できます。

`~sforce=`*single-char* と入力して改行します。*single-char* には任意の 1 文字を指定します。*single-char* を省略するとフォース文字はヌル文字になり、`Ctrl+2` または `Ctrl+Space` を押すことで入力できます。*single-char* として使い勝手がよいのは `Shift+Ctrl+6` で、一部のターミナルサーバーでしか使われません。

フォース文字を変更するには、`~/.tiprc` に次のように記述します。

```
force=single-char
```

<a id="uppercase"></a>
### 文字が大文字になってしまう場合

これは、`tip` の「大文字化文字（raise character）」である `Ctrl+A` を押したときに発生します。この機能は CapsLock キーが壊れた人のために特別に用意されたものです。`~s` を使って `raisechar` を適切な文字に設定してください。フォース文字と大文字化文字のどちらも使わないのであれば、両方に同じ文字を設定しても構いません。

`Ctrl+2` と `Ctrl+A` を入力する必要がある Emacs ユーザー向けの `~/.tiprc` の例を次に示します。

```
force=^^
raisechar=^^
```

この `^^` は `Shift+Ctrl+6` を表します。

<a id="tip-filetransfer"></a>
### `tip` を使ったファイル転送

別の UNIX® 系オペレーティングシステムと通信している場合、`~p`（put）と `~t`（take）を使ってファイルの送受信ができます。これらのコマンドはリモートシステム上で `cat` と `echo` を実行してファイルの受け取りと送信を行います。構文は次のとおりです。

* `~p` *local-file* [ *remote-file* ]
* `~t` *remote-file* [ *local-file* ]

エラーチェックは行われないため、通常は zmodem のような別のプロトコルを使う方が望ましいでしょう。

<a id="zmodem-tip"></a>
### `tip` で zmodem を使うには

ファイルを受信するには、リモート側で送信プログラムを起動したあと、ローカルで `~C rz` と入力して受信を開始します。

ファイルを送信するには、リモート側で受信プログラムを起動したあと、`~C sz` *files* と入力してリモートシステムへ送信します。

<a id="serialconsole-setup"></a>
## シリアルコンソールの設定

FreeBSD には、シリアルポートに接続したダム端末をコンソールとしてシステムを起動する機能があります。この構成は、キーボードやモニタを接続していないマシンへ FreeBSD をインストールしたいシステム管理者や、カーネルやデバイスドライバをデバッグしたい開発者にとって有用です。

[FreeBSD の起動プロセス](14-boot.md#boot)で説明されているように、FreeBSD は 3 段階のブートストラップを採用しています。最初の 2 段階はブートディスク上の FreeBSD スライス先頭に格納されたブートブロックコード内にあり、そのブートブロックが第 3 段階のコードとしてブートローダを読み込んで実行します。

シリアルコンソールからの起動を設定するには、ブートブロックコード、ブートローダコード、およびカーネルを設定する必要があります。

<a id="serialconsole-howto-fast"></a>
### シリアルコンソールの簡易設定

この節では、シリアルコンソールを設定する手順の概要を簡潔に説明します。この手順は、ダム端末が `COM1` に接続されている場合に使用できます。

**手順: `COM1` でのシリアルコンソール設定**

1. シリアルケーブルを `COM1` と制御用の端末に接続します。
2. 起動メッセージがシリアルコンソールに表示されるよう設定するため、スーパーユーザーで次のコマンドを実行します。

```shell
# echo 'console="comconsole"' >> /boot/loader.conf
```

3. `/etc/ttys` を編集し、`ttyu0` エントリの `off` を `on` に、`dialup` を `vt100` に変更します。これを行わないと、シリアルコンソール経由で接続する際にパスワードが要求されなくなり、セキュリティホールとなるおそれがあります。
4. システムを再起動し、変更が反映されたか確認します。

上記とは異なる構成が必要な場合は、より詳しい設定方法を説明している次の節を参照してください。

<a id="serialconsole-howto"></a>
### シリアルコンソールの詳細な設定

この節では、FreeBSD でシリアルコンソールを設定するために必要な手順をより詳しく説明します。

**手順: シリアルコンソールの設定**

1. シリアルケーブルを用意します。

   ヌルモデムケーブル、または標準シリアルケーブルとヌルモデムアダプタの組み合わせを使用します。シリアルケーブルについては、[シリアルケーブルとポート](#term-cables-null)を参照してください。

2. キーボードを取り外します。

   多くのシステムは電源投入時自己診断（POST）の際にキーボードを検出しようとし、キーボードが見つからないとエラーを出します。マシンによっては、キーボードが接続されるまで起動を拒否するものもあります。

   コンピュータがエラーを報告してもそのまま起動する場合は、追加の設定は不要です。

   キーボードなしでの起動を拒否する場合は、このエラーを無視するように BIOS を設定してください。設定方法の詳細はマザーボードのマニュアルを参照してください。

> **ヒント**: BIOS でキーボードの設定を「Not installed」にしてみてください。これにより、電源投入時に BIOS がキーボードを検出しなくなり、キーボードがなくてもエラーが出なくなるはずです。BIOS にこの項目がない場合は、代わりに「Halt on Error」という項目を探し、「All but Keyboard」または「No Errors」に設定しても同様の効果が得られます。

   システムに PS/2® マウスが接続されている場合は、それも取り外してください。PS/2® マウスはキーボードと一部のハードウェアを共有しているため、マウスを接続したままにすると、キーボード検出処理がキーボードはまだ接続されていると誤認することがあります。

> **注**: ほとんどのシステムはキーボードなしで起動しますが、グラフィックスアダプタなしでは起動しないシステムも少なくありません。システムによっては、BIOS 設定で「graphics adapter」の項目を「Not installed」に変更することでグラフィックスアダプタなしで起動できるように設定できます。このオプションに対応していないシステムでは、ディスプレイハードウェアがないと起動を拒否します。そうしたマシンでは、古いモノクロボードであっても構わないので何らかのグラフィックスカードを挿したままにしてください。モニタを接続する必要はありません。

3. ダム端末、モデムプログラムを動かした古いコンピュータ、または別の UNIX® マシンのシリアルポートを、対象のシリアルポートへ接続します。
4. そのシリアルポートに対応する適切な `hint.uart.*` エントリを `/boot/device.hints` に追加します。一部のマルチポートカードではカーネル設定オプションも必要になります。サポートされている各シリアルポートに必要なオプションとデバイスヒントについては、`uart(4)` の man ページを参照してください。
5. 起動ドライブの `a` パーティションのルートディレクトリに `boot.config` を作成します。

   このファイルは、システムをどのように起動するかをブートブロックコードへ指示します。シリアルコンソールを有効にするには、次のオプションのうち 1 つ以上が必要です。複数のオプションを使う場合は、すべて同じ行に記述してください。

   **`-h`**
   : 内蔵コンソールとシリアルコンソールを切り替えます。コンソールデバイスの切り替えに使用します。たとえば、内蔵（ビデオ）コンソールから起動する場合に `-h` を指定すると、ブートローダとカーネルはシリアルポートをコンソールデバイスとして使用するようになります。逆に、シリアルポートから起動する場合に `-h` を指定すると、ブートローダとカーネルはビデオディスプレイをコンソールとして使用するようになります。

   **`-D`**
   : シングルコンソール構成とデュアルコンソール構成を切り替えます。シングル構成では、`-h` の状態に応じて内蔵コンソール（ビデオディスプレイ）またはシリアルポートのいずれか一方がコンソールになります。デュアルコンソール構成では、`-h` の状態にかかわらず、ビデオディスプレイとシリアルポートの両方が同時にコンソールになります。ただし、デュアルコンソール構成が有効なのはブートブロックの実行中のみです。ブートローダへ制御が移ると、`-h` で指定されたコンソールのみが使用されます。

   **`-P`**
   : ブートブロックにキーボードの有無を検出させます。キーボードが見つからない場合、`-D` と `-h` のオプションが自動的に設定されます。

> **注**: 現行バージョンのブートブロックでは容量の制約があるため、`-P` が検出できるのは拡張キーボードのみです。101 キー未満で F11・F12 キーを持たないキーボードは検出されない場合があります。この制約により、一部のノートパソコンのキーボードは正しく検出されないことがあります。その場合は `-P` を使用しないでください。

   コンソールを自動選択するには `-P`、シリアルコンソールを有効にするには `-h` のいずれかを使用します。詳細は `boot(8)` および `boot.config(5)` の man ページを参照してください。

   `-P` を除くオプションはブートローダへ引き継がれます。ブートローダは `-h` の状態を調べて、内蔵ビデオとシリアルポートのどちらをコンソールにするかを決定します。つまり、`/boot.config` に `-D` を指定して `-h` を指定しなかった場合、シリアルポートをコンソールとして使用できるのはブートブロックの段階だけであり、ブートローダは内蔵ビデオディスプレイをコンソールとして使用します。

6. マシンを起動します。

   FreeBSD が起動すると、ブートブロックは `/boot.config` の内容をコンソールへエコー出力します。例を示します。

```shell
/boot.config: -P
Keyboard: no
```

   2 行目は `/boot.config` に `-P` が指定されている場合にのみ表示され、キーボードの有無を示します。これらのメッセージは、`/boot.config` のオプションに応じてシリアルコンソール、内蔵コンソール、またはその両方へ出力されます。

| オプション | メッセージの出力先 |
|---|---|
| なし | 内蔵コンソール |
| `-h` | シリアルコンソール |
| `-D` | シリアルコンソールおよび内蔵コンソール |
| `-Dh` | シリアルコンソールおよび内蔵コンソール |
| `-P`（キーボードあり） | 内蔵コンソール |
| `-P`（キーボードなし） | シリアルコンソール |

   このメッセージのあと、ブートブロックがブートローダの読み込みを続行して次のメッセージをコンソールに出力するまでの間に、わずかな待ち時間があります。通常はブートブロックに割り込む必要はありませんが、設定が正しいか確認するために割り込むこともできます。

   起動処理に割り込むには、コンソールで `Enter` 以外の任意のキーを押します。すると、ブートブロックは次のようなプロンプトを表示して指示を待ちます。

```shell
>> FreeBSD/i386 BOOT
Default: 0:ad(0,a)/boot/loader
boot:
```

   `/boot.config` のオプションどおり、上記のメッセージがシリアルコンソール、内蔵コンソール、またはその両方に表示されていることを確認します。正しいコンソールにメッセージが表示されていれば、`Enter` キーを押して起動処理を続行します。

   シリアル端末にプロンプトが表示されない場合は、設定に誤りがあります。`-h` と入力して `Enter` または `Return` キーを押すことで、ブートブロック（およびその後のブートローダとカーネル）にシリアルポートをコンソールとして選ぶよう指示できます。システムが起動したら、どこに問題があったか確認してください。

起動処理の第 3 段階であっても、ブートローダで適切な環境変数を設定すれば、内蔵コンソールとシリアルコンソールを切り替えることができます。詳細は `loader(8)` の man ページを参照してください。

> **注**: `/boot/loader.conf` または `/boot/loader.conf.local` に次の行を記述すると、`/boot.config` のオプションにかかわらず、ブートローダとカーネルが起動メッセージをシリアルコンソールへ出力するように設定されます。

```
console="comconsole"
```

> この行は、起動メッセージができるだけ早い段階でシリアルコンソールに表示されるよう、`/boot/loader.conf` の先頭行に記述してください。
>
> この行が存在しない場合、または `console="vidconsole"` に設定されている場合、ブートローダとカーネルはブートブロックの `-h` で指定された方のコンソールを使用します。詳細は `loader.conf(5)` の man ページを参照してください。
>
> 現時点では、ブートローダにはブートブロックの `-P` に相当するオプションがなく、キーボードの有無に基づいて内蔵コンソールとシリアルコンソールを自動選択する仕組みはありません。

> **ヒント**: 必須ではありませんが、シリアル回線上で `login` プロンプトを提供することもできます。これを設定するには、[端末の設定](#term-config)の手順に従って `/etc/ttys` のシリアルポート用エントリを編集します。シリアルポートの速度を変更した場合は、新しい設定に合わせて `std.115200` も変更してください。

<a id="chapter-30-heading-27"></a>
### シリアルポートの通信速度を高速化する

デフォルトでは、シリアルポートの設定は 115200 ボー、8 ビット、パリティなし、ストップビット 1 です。デフォルトのコンソール速度を変更するには、次のいずれかの方法を使用します。

* `/etc/make.conf` を編集し、`BOOT_COMCONSOLE_SPEED` に新しいコンソール速度を設定します。その後、ブートブロックとブートローダを再コンパイルしてインストールします。

```shell
# cd /sys/boot
# make clean
# make
# make install
```

  `-h` 付きでの起動以外の方法でシリアルコンソールを設定している場合や、カーネルが使用するシリアルコンソールがブートブロックで使用するものと異なる場合は、カスタムカーネル設定ファイルに希望の速度で次のオプションを追加し、新しいカーネルをコンパイルします。

```
options CONSPEED=19200
```

* `/boot.config` に `-S`*19200* ブートオプションを追加します（*19200* の部分は使用する速度に置き換えてください）。
* `/boot/loader.conf` に次のオプションを追加します（*115200* の部分は使用する速度に置き換えてください）。

```
boot_multicons="YES"
boot_serial="YES"
comconsole_speed="115200"
console="comconsole,vidconsole"
```

<a id="serialconsole-ddb"></a>
### シリアル回線から DDB デバッガへ入る

シリアルコンソールからカーネルデバッガへ入れるように設定するには、[FreeBSD カーネルの設定](09-kernelconfig.md#kernelconfig)の手順に従って、カスタムカーネル設定ファイルに次のオプションを追加し、カーネルをコンパイルします。これはリモート診断には便利ですが、シリアルポート上で誤った BREAK 信号が発生した場合に危険を伴う点に注意してください。カーネルデバッガの詳細は `ddb(4)` および `ddb(8)` の man ページを参照してください。

```
options BREAK_TO_DEBUGGER
options DDB
```
